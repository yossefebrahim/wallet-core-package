## 1. Scope and assumptions

### 1.1 In scope

Everything in this repository is glue: the parts between a consuming Flutter app and upstream's C interface. PRD §16 S1 states the consequence plainly — upstream reviews of wallet-core say nothing about the code we write. In scope:

- **Wrappers** — the `TWData`/`TWString` ownership wrappers, `Disposable`, finalizers, scopes, and the leak tracker in `wallet_core_flutter_bindings` (T1.6).
- **Loader** — artifact acquisition at build time, SHA-256 verification against `compat_manifest.json`, library location and loading, symbol lookup, build-identity and release-set verification in `wallet_core_flutter_native` (T1.2, T1.7).
- **Worker** — the signing-worker isolate, its message protocol, session state machine, queue, timeouts, cancellation, and shutdown (PRD §14.3, T2.1). In M0 the same protocol runs on an in-process executor in the caller's isolate (§1.3 boundary 1).
- **Signer** — key resolution from `KeyLocator`s, key injection into the signing input, and the family boundary `encodeKeylessInput` / `parseSigningOutput` (PRD §11.4, T1.12, T2.0).
- **Adapter** — the optional thin native shim of PRD §11.4 Approach B, if DECISION-1 selects it (T1.13).
- **Native build** — the build workflow and scripts that produce our artifacts from the pinned upstream commit (`.github/workflows/build-native.yml`, `tools/native_build/`, T1.2), including every change they make to upstream's build (TM-33, TM-34).
- **Docs** — the guidance we give app developers, because for a large class of threats below the only mitigation available to this SDK is telling the developer what the SDK does not do (T1.18, T3.10, T3.13). The example app (T1.16) is guidance of this kind (TM-32).

Protobuf construction in Dart is in scope wherever it appears: encoding a signing input is our code even though the bytes it produces are upstream's format.

### 1.2 Out of scope

- **Upstream cryptography and chain logic.** Key generation, derivation, hashing, curve operations, and signed-transaction serialization are wallet-core's. A defect in them is an upstream vulnerability, handled by TM-27, not by a mitigation here.
- **The host operating system and device.** A rooted or jailbroken device, a malicious OS image, a hostile debugger attached to the process, physical memory extraction, and swap contents are outside anything this SDK can defend. PRD §11.3 says so; §5 below repeats it.
- **The consuming app's own storage, UI, and network.** Where the app persists an encrypted keystore, how it collects a mnemonic from the user, whether it screenshots its own seed screen, and what it sends to its backend are the app's decisions. We document patterns (PRD §16 S7); we ship none.
- **Broadcasting, RPC, balances, fees, and nonces.** Out of product scope entirely (PRD §6), therefore out of threat scope.
- **The consuming app's build pipeline.** We verify our artifacts against a manifest we ship; we cannot verify the app's own toolchain.

### 1.3 Trust boundaries

1. **Dart UI isolate ↔ signing worker isolate.** *Design (PRD §14.2, DECISION-12):* messages cross; native pointers never do; the UI isolate holds opaque refs and plain values only. *As built (M0):* there is no second isolate. The session reaches its executor through the `WorkerTransport` seam, and the only transport that exists is `InProcessTransport`, which runs `WorkerLoop` and `EngineRequestHandler` on the calling isolate's event loop[^b1-transport]. What holds today is a **protocol** boundary: every request and reply is a plain value with no native pointer, handle, or port (`docs/architecture/lifecycle.md` §6); requests and replies are delivered asynchronously, never inside the public call that submitted them; the executor receives its own copy of the one secret buffer a request owns (an `ImportWallet`'s entropy) and the sender's copy is overwritten before `send` returns[^b1-copy]; and public proxies hold an integer ref, never a `Pointer` (TM-23). What does **not** hold today is memory isolation: every copy of a secret that `docs/security/memory_contract.md` lists lives in the application's own isolate ("Where the executor runs in this version"), and a native call blocks the application's event loop for its duration, so no session timer fires during it[^b1-block]. **T2.1 adds** a worker isolate running the same loop over the same protocol, a `SendPort` transport that maps the isolate's `onError`/`onExit` to `WorkerTerminatedError(uncaughtDartError | isolateExited)`, an envelope that carries each operation's `OperationDeadline`, and a public cancel-before-start (DECISION-12 §3.5 and its 2026-10-03 amendment, item 3). Until then "native pointers never cross" holds because there is nothing to cross, not because an isolate separates them.
2. **Dart (any isolate) ↔ native library.** The FFI call boundary: lengths, pointers, and serialized bytes cross in both directions; everything returning from native is untrusted input to Dart (TM-17 … TM-21).
3. **Build machine ↔ artifact host.** The only place this project touches the network (PRD §16 S4). Everything crossing it is verified against a checksum checked into this repository. *As built:* the build-time fetcher exists (TM-14), but no artifact set has been published and the manifest's artifact digests are still `TBD-T1.2` placeholders (TM-14, TM-15). The CI build of our artifacts also crosses this boundary in the other direction — it downloads upstream's source and release asset and runs upstream's build tooling (TM-15, TM-33).
4. **Package consumer ↔ published package set.** pub.dev delivery of three packages that must agree on a release-set id and a manifest hash (PRD §15.4). *As built:* neither cross-check runs on the default `initialize()` path yet (TM-16).
5. **This SDK ↔ the consuming app.** The public API is the boundary; `advanced.dart` is an explicit opt-out of it, where the caller accepts the ownership and secret-handling responsibilities of PRD §11 (PRD §8).
6. **This SDK ↔ upstream wallet-core.** A pinned commit, generated bindings, and a behavioral diff over the vector inventory (PRD §15.2) are the whole of what we assert about the code on the other side.

### 1.4 Assumptions

- Upstream handles (`TWHDWallet`, `TWPrivateKey`, …) are assumed **not** thread-safe; nothing shares a handle across isolates (PRD §14.1).
- `TWDataDelete` and `TWStringDelete` wipe the buffer the object currently owns before freeing it (PRD §11.1, verified). Nothing beyond that current buffer is wiped.
- `NativeFinalizer` cannot run Dart code and its timing is bounded only by isolate-group shutdown; the managed Dart `Finalizer` *can* run Dart code and therefore can post a message to the owning isolate. The design uses the managed finalizer on public proxies as a fallback and the native finalizer on internal handles (PRD §11.2 items 5 and 8).
- Upstream 4.8.0 signing-input protobufs embed private keys (Bitcoin: `repeated bytes private_key`; Solana: `private_key`, `fee_payer_private_key`, `nonce_account_private_key`; Ethereum: `private_key`). The key-less request design and signer-owned injection exist precisely because of this, and every threat about key material in Dart memory traces back to it.
- The SDK makes no network call at runtime (PRD §16 S4), so remote attack surface at runtime is limited to data the app itself hands us. Today this is enforced by a static lint, not by a runtime test (TM-10).

## 2. Assets

| Asset | Where it lives in our design | Why it matters |
|---|---|---|
| **Mnemonic** | Caller's `String` on import; a Dart `String` on export. It crosses the worker boundary whole in three of the eight secret-bearing payloads DECISION-12 §3.2 enumerates (amended 2026-10-03), and only those three: outward in `ImportWallet` and `ValidateMnemonic`, back in `MnemonicExported` (the reply to `ExportMnemonic`, which is also how a newly created wallet's mnemonic is obtained — `WalletCreated` carries none); a word or a prefix of one crosses in three more (`ValidateMnemonicWord`, `SuggestMnemonicWords`, and the reply `MnemonicWordsSuggested`). In M0 "crossing" means passing through the in-process executor in the same isolate (§1.3 boundary 1) | Full compromise of every account derived from it |
| **Seed / master key** | Inside upstream's `TWHDWallet`, owned by the worker isolate (in M0, by the in-process executor) | Same as the mnemonic |
| **BIP-39 passphrase** | Caller-supplied `String`, passed through to upstream wallet creation | A wallet cannot be reconstructed from the mnemonic without it; also a second secret to leak |
| **Derived private keys** | Derived inside the worker for one operation, disposed immediately after; the key is read through a `Uint8List` view over upstream's `TWData`, prepended to the key-less input in one SDK-allocated `calloc` staging buffer that is zeroed and freed after `TWDataCreateWithBytes` copies it; residual copies are upstream's own (`TWPrivateKey`, the key `TWData`, the keyed-input `TWData`, each released before the reply; plus the copies upstream's Rust signing path makes and frees unwiped) | Compromise of one account |
| **Keystore password** | Caller-supplied `String` for `StoredKey` import/export (not built yet, T3.4) | Unlocks the encrypted keystore the app persists |
| **Encrypted keystore (`StoredKey`) blob** | Produced by upstream, persisted by the app, never by us | Offline password attack if exfiltrated |
| **Unsigned transaction request** | Plain Dart value types, crossing isolates freely, key-less by construction | Integrity: a modified request signs the attacker's transaction |
| **Signed transaction / signature** | Returned as a sealed `SignResult` | Integrity and, in some flows, privacy; a signature over the wrong payload is the worst outcome of a signing SDK |
| **Native artifacts** | Fetched at build time, checksum-pinned, loaded at runtime. None published yet (TM-14) | Substitution replaces all of upstream's cryptography with the attacker's |
| **Compatibility manifest** | `compat_manifest.json`, checked into this repo and shipped inside the packages; its identity, digest and toolchain fields are `TBD-T1.2` placeholders until the first artifact set exists | It *is* the integrity root for the artifacts; tampering with it defeats TM-14 and TM-15 |
| **Test-vector inventory** | `test_vectors/`, with provenance per entry | A wrong "tested" claim is a security claim we cannot support |

## 3. Actors

| Actor | Capability we assume | Motivation |
|---|---|---|
| **Consuming app developer** | Writes the app around us; can misuse the API, log anything, and opt into `advanced.dart` | Not hostile, but the most likely cause of a key leak; the primary audience of §4's "documented" mitigations |
| **End user** | Types a mnemonic, screenshots a seed screen, pastes an address | Not hostile; the source of the platform-surface exposures of TM-07 … TM-12 and TM-32 |
| **Malicious app on the same device** | Reads the clipboard, reads world-readable files, observes the app's public surface; on a compromised device, more | Steal a mnemonic or key in transit through a shared OS surface |
| **Malicious network** | Full control of any build-time HTTP the loader performs | Substitute a native artifact (TM-14) |
| **Compromised CI or artifact host** | Can publish or replace artifacts and release assets under our name | Ship a backdoored library to every consumer at once — the highest-impact threat in this model |
| **Compromised dependency** | Code execution inside our build or inside the consumer's app process via a transitive package | Exfiltrate secrets from process memory, or tamper with the manifest before verification |
| **Hostile counterparty supplying data** | Controls a transaction request's contents, or (in a compromised-library scenario) the bytes upstream returns | Get a signature over something the user did not intend; corrupt our parsing (TM-17 … TM-22) |

## 4. Threats

Component labels: **wrappers** (bindings memory layer), **worker** (signing isolate and protocol; in M0 the in-process executor), **loader** (native package: fetch, verify, load; and the native build that produces what it loads), **signer** (key resolution, injection, family encode/parse), **adapter** (Approach B shim, if chosen), **docs** (guidance we publish, including the example app), **process** (CI and review).

Owners are task ids from `docs/plan/phases/`, or "app developer, documented in …" where the SDK cannot act. "(built)" after an owner means the code that owner delivered is on `main` and is what the row's evidence cites.

### 4.1 Key material lifecycle

The SDK cannot reach any of these surfaces. Its obligations are (a) never to put a secret on one itself, and (b) to state clearly which of them the app must handle.

## 5. What we deliberately do not promise

These are limitations of the design, chosen knowingly and stated so that nobody builds on a guarantee that does not exist. They mirror PRD §11.3.

1. **We do not promise that every copy of a secret is erased.** When a wrapper is disposed, upstream wipes the buffer that object currently owns — that much is guaranteed. Beyond it, copies can exist in Dart heap objects (`Uint8List`, `String`, protobuf messages, serialized bytes), in earlier native allocations upstream reallocated internally, in the GC's copying and compaction history, in platform keyboard and clipboard buffers, in crash dumps, and in swap. Dart provides no API to pin or erase managed memory. Overwriting our own buffers narrows the window; it does not close it.
2. **We do not defend against a compromised host.** A rooted or jailbroken device, a hostile OS, an attached debugger, a malicious keyboard, or physical memory extraction defeats every mitigation in §4. The SDK's threat model assumes the device is honest.
3. **We do not promise that a mnemonic or passphrase the caller gave us, or that we returned, is gone.** Import accepts a `String`; export returns one. We drop our own references as soon as the native wallet exists. The caller's copy and the platform's copies are beyond reach.
4. **We do not claim upstream's security reviews cover this code.** Reviews of wallet-core say nothing about the FFI glue, protobuf construction in Dart, artifact acquisition, the loader, the worker, or the signer. An external review of the glue layer is scoped separately (PRD §16 S6, T5.8) and its findings will be recorded, not summarized away.
5. **We do not promise that an independent rebuild of the native artifacts yields byte-identical output.** Checksum verification against the manifest is required from M0 and is what integrity currently rests on; independent-rebuild verification is a separate, later requirement (PRD §12.4, T4.4) whose outcome depends on upstream's build determinism, which we do not control. Until it is demonstrated, the documentation says "checksum-pinned" and nothing stronger.
6. **We do not promise per-coin correctness beyond the tested vectors.** "Exposed" is not "verified". The capability matrix names the exact variants proven by a vector; everything else is labeled exposed-unverified, and signing an unverified variant is the caller's risk.
7. **We ship no storage, no lock timer, no UI protection, and no key backup.** The app owns all of them; §4.2 says which.
