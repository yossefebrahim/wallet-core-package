*v0.1 change note: Updated to match D0 findings and DECISION-12 outcomes on crash handling and ownership.*

This document exists because PRD §16 S6 requires a threat model *before* the worker, loader, and public API are designed. It is an input to T0.11 (DECISION-11 … DECISION-14) and to every Phase 1 and Phase 2 implementation task: each row of §4 names a component and an owning task, and those tasks are expected to design against the named threat rather than rediscover it.

Unofficial Dart/Flutter SDK for the open-source Trust Wallet Core library. Not affiliated with or endorsed by Trust Wallet.

---

## 1. Scope and assumptions

### 1.1 In scope

Everything in this repository is glue: the parts between a consuming Flutter app and upstream's C interface. PRD §16 S1 states the consequence plainly — upstream reviews of wallet-core say nothing about the code we write. In scope:

- **Wrappers** — the `TWData`/`TWString` ownership wrappers, `Disposable`, finalizers, scopes, and the leak tracker in `wallet_core_flutter_bindings` (T1.6).
- **Loader** — artifact acquisition at build time, SHA-256 verification against `compat_manifest.json`, library location and loading, symbol lookup, build-identity and release-set verification in `wallet_core_flutter_native` (T1.2, T1.7).
- **Worker** — the signing-worker isolate, its message protocol, session state machine, queue, timeouts, cancellation, and shutdown (PRD §14.3, T2.1).
- **Signer** — key resolution from `KeyLocator`s, key injection into the signing input, and the family boundary `encodeKeylessInput` / `parseSigningOutput` (PRD §11.4, T1.12, T2.0).
- **Adapter** — the optional thin native shim of PRD §11.4 Approach B, if DECISION-1 selects it (T1.13).
- **Docs** — the guidance we give app developers, because for a large class of threats below the only mitigation available to this SDK is telling the developer what the SDK does not do (T1.18, T3.10, T3.13).

Protobuf construction in Dart is in scope wherever it appears: encoding a signing input is our code even though the bytes it produces are upstream's format.

### 1.2 Out of scope

- **Upstream cryptography and chain logic.** Key generation, derivation, hashing, curve operations, and signed-transaction serialization are wallet-core's. A defect in them is an upstream vulnerability, handled by TM-27, not by a mitigation here.
- **The host operating system and device.** A rooted or jailbroken device, a malicious OS image, a hostile debugger attached to the process, physical memory extraction, and swap contents are outside anything this SDK can defend. PRD §11.3 says so; §5 below repeats it.
- **The consuming app's own storage, UI, and network.** Where the app persists an encrypted keystore, how it collects a mnemonic from the user, whether it screenshots its own seed screen, and what it sends to its backend are the app's decisions. We document patterns (PRD §16 S7); we ship none.
- **Broadcasting, RPC, balances, fees, and nonces.** Out of product scope entirely (PRD §6), therefore out of threat scope.
- **The consuming app's build pipeline.** We verify our artifacts against a manifest we ship; we cannot verify the app's own toolchain.

### 1.3 Trust boundaries

1. **Dart UI isolate ↔ signing worker isolate.** Messages cross; native pointers never do. The UI isolate holds opaque refs and plain values only (PRD §14.2).
2. **Dart (any isolate) ↔ native library.** The FFI call boundary: lengths, pointers, and serialized bytes cross in both directions; everything returning from native is untrusted input to Dart (TM-17 … TM-21).
3. **Build machine ↔ artifact host.** The only place this project touches the network (PRD §16 S4). Everything crossing it is verified against a checksum checked into this repository.
4. **Package consumer ↔ published package set.** pub.dev delivery of three packages that must agree on a release-set id and a manifest hash (PRD §15.4).
5. **This SDK ↔ the consuming app.** The public API is the boundary; `advanced.dart` is an explicit opt-out of it, where the caller accepts the ownership and secret-handling responsibilities of PRD §11 (PRD §8).
6. **This SDK ↔ upstream wallet-core.** A pinned commit, generated bindings, and a behavioral diff over the vector inventory (PRD §15.2) are the whole of what we assert about the code on the other side.

### 1.4 Assumptions

- Upstream handles (`TWHDWallet`, `TWPrivateKey`, …) are assumed **not** thread-safe; nothing shares a handle across isolates (PRD §14.1).
- `TWDataDelete` and `TWStringDelete` wipe the buffer the object currently owns before freeing it (PRD §11.1, verified). Nothing beyond that current buffer is wiped.
- `NativeFinalizer` cannot run Dart code and its timing is bounded only by isolate-group shutdown; the managed Dart `Finalizer` *can* run Dart code and therefore can post a message to the owning isolate. The design uses the managed finalizer on public proxies as a fallback and the native finalizer on internal handles (PRD §11.2 items 5 and 8).
- Upstream 4.8.0 signing-input protobufs embed private keys (Bitcoin: `repeated bytes private_key`; Solana: `private_key`, `fee_payer_private_key`, `nonce_account_private_key`; Ethereum: `private_key`). The key-less request design and signer-owned injection exist precisely because of this, and every threat about key material in Dart memory traces back to it.
- The SDK makes no network call at runtime (PRD §16 S4), so remote attack surface at runtime is limited to data the app itself hands us.

## 2. Assets

| Asset | Where it lives in our design | Why it matters |
|---|---|---|
| **Mnemonic** | Caller's `String` on import; a Dart `String` on export. It crosses the worker boundary whole in three of the eight secret-bearing payloads DECISION-12 §3.2 enumerates (amended 2026-10-03), and only those three: outward in `ImportWallet` and `ValidateMnemonic`, back in `MnemonicExported` (the reply to `ExportMnemonic`, which is also how a newly created wallet's mnemonic is obtained — `WalletCreated` carries none); a word or a prefix of one crosses in three more (`ValidateMnemonicWord`, `SuggestMnemonicWords`, and the reply `MnemonicWordsSuggested`) | Full compromise of every account derived from it |
| **Seed / master key** | Inside upstream's `TWHDWallet`, owned by the worker isolate | Same as the mnemonic |
| **BIP-39 passphrase** | Caller-supplied `String`, passed through to upstream wallet creation | A wallet cannot be reconstructed from the mnemonic without it; also a second secret to leak |
| **Derived private keys** | Derived inside the worker for one operation, disposed immediately after; serialized into the signing input under Approach A | Compromise of one account |
| **Keystore password** | Caller-supplied `String` for `StoredKey` import/export | Unlocks the encrypted keystore the app persists |
| **Encrypted keystore (`StoredKey`) blob** | Produced by upstream, persisted by the app, never by us | Offline password attack if exfiltrated |
| **Unsigned transaction request** | Plain Dart value types, crossing isolates freely, key-less by construction | Integrity: a modified request signs the attacker's transaction |
| **Signed transaction / signature** | Returned as a sealed `SignResult` | Integrity and, in some flows, privacy; a signature over the wrong payload is the worst outcome of a signing SDK |
| **Native artifacts** | Fetched at build time, checksum-pinned, loaded at runtime | Substitution replaces all of upstream's cryptography with the attacker's |
| **Compatibility manifest** | `compat_manifest.json`, checked into this repo and shipped inside the packages | It *is* the integrity root for the artifacts; tampering with it defeats TM-14 and TM-15 |
| **Test-vector inventory** | `test_vectors/`, with provenance per entry | A wrong "tested" claim is a security claim we cannot support |

## 3. Actors

| Actor | Capability we assume | Motivation |
|---|---|---|
| **Consuming app developer** | Writes the app around us; can misuse the API, log anything, and opt into `advanced.dart` | Not hostile, but the most likely cause of a key leak; the primary audience of §4's "documented" mitigations |
| **End user** | Types a mnemonic, screenshots a seed screen, pastes an address | Not hostile; the source of the platform-surface exposures of TM-07 … TM-12 |
| **Malicious app on the same device** | Reads the clipboard, reads world-readable files, observes the app's public surface; on a compromised device, more | Steal a mnemonic or key in transit through a shared OS surface |
| **Malicious network** | Full control of any build-time HTTP the loader performs | Substitute a native artifact (TM-14) |
| **Compromised CI or artifact host** | Can publish or replace artifacts and release assets under our name | Ship a backdoored library to every consumer at once — the highest-impact threat in this model |
| **Compromised dependency** | Code execution inside our build or inside the consumer's app process via a transitive package | Exfiltrate secrets from process memory, or tamper with the manifest before verification |
| **Hostile counterparty supplying data** | Controls a transaction request's contents, or (in a compromised-library scenario) the bytes upstream returns | Get a signature over something the user did not intend; corrupt our parsing (TM-17 … TM-22) |

## 4. Threats

Component labels: **wrappers** (bindings memory layer), **worker** (signing isolate and protocol), **loader** (native package: fetch, verify, load), **signer** (key resolution, injection, family encode/parse), **adapter** (Approach B shim, if chosen), **docs** (guidance we publish).

Owners are task ids from `docs/plan/phases/`, or "app developer, documented in …" where the SDK cannot act.

### 4.1 Key material lifecycle

| # | Threat | Component | Mitigation | Owner | Residual risk |
|---|---|---|---|---|---|
| TM-01 | **Key residence time.** A derived private key stays live in native or Dart memory longer than the operation that needed it — kept in a cache, held by a long-lived signer object, or left in an undisposed wrapper | worker, signer, wrappers | Keys are derived inside the worker for one signing operation and disposed immediately afterwards (PRD §14.2); every temporary native allocation is released in a `finally` block (§11.2 item 4); no key cache exists in 1.0; the leak tracker reports any wrapper finalized without an explicit dispose | T2.1 (worker), T1.12 / T2.0 (signer), T1.6 (wrappers, leak tracker) | Under Approach A the serialized `SigningInput` holds the key in a Dart `Uint8List` whose GC-internal copies cannot be erased (PRD §11.3). Overwriting our own buffer reduces, and does not remove, the window |
| TM-02 | **No lock/unlock state.** A session holds a wallet handle for the app's whole lifetime; there is no "locked" state in which the seed is not resident | worker, docs | 1.0 defines lock as a session operation, not a flag: `wallet.close()` frees the handle, `WalletCore.shutdown()` terminates the worker and frees everything; unlock is re-import from an encrypted `StoredKey` with the user's password. The cookbook states this explicitly rather than implying an auto-lock exists | T3.4 (`StoredKey`), T3.10 (cookbook), T1.11 (session states) | An app that never calls `shutdown()` keeps the seed native-resident until process exit. The SDK cannot enforce a policy it does not own |
| TM-03 | **App backgrounding and auto-lock guidance.** The app is suspended with an unlocked session; the OS snapshots the UI, and the process may be killed without running any handler | docs, worker | Documented pattern: shut the session down on the app-lifecycle transition to background/paused and re-initialize on resume; an idle auto-lock timer, if the app wants one, is built from the same two calls and is the app's policy. The SDK does not hook `WidgetsBindingObserver` itself — that is the app's lifecycle, and a hidden hook would be worse than a documented one | app developer, documented in `docs/cookbook/` (T3.10); session teardown by T1.11 / T2.1 | The OS may snapshot the foreground frame *before* the handler runs; a kill skips finalizers entirely (`NativeFinalizer` explicitly does not run on process exit, PRD §11.1) |
| TM-04 | **BIP-39 passphrase.** The passphrase crosses the isolate boundary in the `ImportWallet` and `CreateWallet` messages as a Dart `String`, is unerasable, and is silently load-bearing: the same mnemonic with a different passphrase is a different wallet | signer, worker, docs | Passphrase-carrying import is an explicitly listed entry in the v1 feature/exclusion table (PRD §16 S9), not an undocumented capability; the "what we wipe / what we can't" page covers it beside the mnemonic; both messages are named in the protocol, which enumerates a **closed set of eight secret-bearing payloads** (amended 2026-10-03) — the requests `CreateWallet`, `ImportWallet`, `ImportKey` (planned), `ValidateMnemonic`, `ValidateMnemonicWord` and `SuggestMnemonicWords`, and the replies `MnemonicExported` and `MnemonicWordsSuggested` (DECISION-12 §3.2) — so a ninth cannot be added without reopening that record | T3.13 (S9 table), T1.18 (memory doc), T0.11 / DECISION-12 (protocol) | A Dart `String` cannot be erased. Copies survive in the heap until GC and possibly beyond |
| TM-05 | **Keystore password.** `StoredKey` import/export takes a password as a Dart `String`; a weak password makes an exfiltrated keystore an offline attack | wrappers, docs, signer | Encryption is upstream's; we pass the password straight through and keep no copy. Cookbook steers to platform secure storage for the keystore blob and states that the SDK persists nothing itself (PRD §16 S7). No password is ever placed in an error message | T3.4, T3.10, T1.18 | Password copies in the Dart heap and in the platform text-input buffers are unreachable to us; password strength is the app's policy |
| TM-06 | **Mnemonic export and display.** `exportMnemonic()` necessarily returns a `String` so the app can show it to the user | docs, worker | Documented as unerasable, with the recommended pattern of displaying once and dropping references; the value crosses the isolate boundary only on explicit request, through the one reply type that may carry it (`MnemonicExported`, DECISION-12 §3.2) — including for a freshly created wallet, whose `WalletCreated` reply carries no mnemonic, so there is a single path to review and to test | T1.18, T3.10 | Unbounded: the string lives until GC, and the app may put it anywhere. This is a designed limitation, not a defect |

### 4.2 Platform and app-surface leakage

The SDK cannot reach any of these surfaces. Its obligations are (a) never to put a secret on one itself, and (b) to state clearly which of them the app must handle.

| # | Threat | Component | Mitigation | Owner | Residual risk |
|---|---|---|---|---|---|
| TM-07 | **Clipboard.** The user copies a mnemonic or private key; another app on the device reads the system clipboard | docs | The SDK never writes to the clipboard. Cookbook states that copy-to-clipboard for seed phrases is a device-wide exposure and names the platform mitigations (Android `EXTRA_IS_SENSITIVE`, clearing after a timeout) as the app's job | app developer, documented in `docs/cookbook/` (T3.10) | Total once the user copies; the clipboard is a shared OS surface |
| TM-08 | **Keyboard.** Mnemonic entry passes through the platform IME, which may cache, learn, or sync it | docs | Documented: use a text field configured to disable suggestions/autocorrect and personalized learning for seed input; the SDK's mnemonic-import path drops its own references once the native wallet exists but cannot reach the IME buffer (PRD §11.3) | app developer, documented in `docs/cookbook/` (T3.10) | A third-party keyboard can capture everything typed; unmitigable from our side |
| TM-09 | **Logs.** A secret reaches `stdout`, logcat, or the app's logging framework through an exception message, a `toString()`, or a debug print in our code | wrappers, worker, signer, docs | No `toString()` on any SDK or wrapper type includes key material, mnemonic text, passwords, or raw signing-input bytes; typed errors carry an upstream code and a message but never the offending secret payload; no `print` in shipped code paths; a test asserts that error and `toString()` output for secret-bearing types contains no input material | T1.11 and T2.0 (error types), T1.6 (wrappers), T2.12 (assertions in the hostile-input suite) | The app can log whatever it holds, including a mnemonic it just received from us |
| TM-10 | **Analytics.** An app's analytics SDK, or a transitive dependency of ours, ships process data off the device | docs, loader | No package in the three packages' runtime dependency sets may perform networking; a no-network test runs the example with networking disabled; build-time fetch is the loader's only network use and is measured separately (PRD §16 S4) | T1.17 (no-network test, dependency policy), T3.10 (docs) | Another dependency of the *app* can read anything in the app's process. Our dependency policy binds only our packages |
| TM-11 | **Crash dumps.** A crash reporter captures heap contents, or an unhandled error's stack captures a secret-bearing frame | docs, worker, wrappers | Same discipline as TM-09: secrets are never arguments visible in messages we construct; the leak tracker's creation stack traces record allocation sites, never contents (see TM-30); cookbook advises scrubbing or disabling heap capture in crash reporters for wallet apps | T1.6, T3.10, T1.18 | A native or Dart heap dump taken by the OS or a reporter can contain any live secret; nothing in Dart can prevent this |
| TM-12 | **Screenshots and screen recording.** The seed-display or transaction-confirm screen is captured, by the user, by the OS task switcher, or by a screen recorder | docs | Documented as the app's control: `FLAG_SECURE` on Android and a covering view on iOS backgrounding for any screen that shows a mnemonic | app developer, documented in `docs/cookbook/` (T3.10) | Out of our reach; the SDK draws no UI |

### 4.3 Artifact and load-path integrity

| # | Threat | Component | Mitigation | Owner | Residual risk |
|---|---|---|---|---|---|
| TM-13 | **Dynamic-library path hijacking.** The loader is induced to open an attacker-supplied library — via a search path, an environment variable, a relative path, or a consumer-configurable location — and every "upstream" call then runs attacker code | loader | The library is resolved by the packaging mechanism's own asset identity (bundled asset for build hooks, AAR/xcframework for conventional packaging), never from a caller-supplied path, `LD_LIBRARY_PATH`, or a working-directory-relative name. The vendored/offline mode accepts a directory only from build-time configuration, never at runtime, and applies the same checksum check as a fetch. After load, `WalletCore.initialize()` calls the build-identity symbol and compares it with the manifest before any other symbol is used (PRD §12.3) | T1.7 (loader, identity check), T1.2 (artifact build), T1.17 (identity-mismatch negative test) | On a rooted or jailbroken device an attacker who can rewrite the app bundle has already won; static linkage on iOS makes runtime hashing meaningless (PRD §12.3), so the identity symbol is an integrity signal about *which build* was linked, not a tamper check |
| TM-14 | **Artifact substitution in transit.** A malicious network replaces the artifact the loader downloads at build time | loader | Every artifact's SHA-256 is pinned in `compat_manifest.json`, which is checked into this repository and shipped inside the package; a mismatch fails the build loudly with no fallback and no "continue anyway" flag; URLs are content-addressed and immutable (PRD §12.3, DECISION-14) | T1.7, T1.2, T0.11 / DECISION-14 | The manifest itself must arrive intact — see TM-16 |
| TM-15 | **Compromised CI or artifact host.** Our own release assets are replaced, or a backdoored build is published under our name, reaching every consumer at once | loader, docs | Checksums are generated in the build workflow and committed to this repository in the same PR that pins them, so a host-side replacement no longer matches a checksum a human reviewed; provenance attestations bind an artifact to the workflow and commit that produced it; a secondary mirror and a published retention policy remove the single point of failure; the release-set id must agree across all three packages at `initialize()` | T1.2 (build workflow), T4.5 (attestations), T3.13 (retention policy), T0.11 / DECISION-14 | A CI compromise that lands both the artifact and the committed checksum in an approved PR defeats this; the remaining control is human review of the pin PR and the diff reports (PRD §15.2 step 6) |
| TM-16 | **Manifest tampering.** The integrity root is modified — in the consumer's `pub` cache, in a fork, or before verification runs | loader | The manifest ships inside the package (pub.dev content hashing covers delivery), is mirrored in the other two packages' metadata, and is cross-checked at runtime: all three packages must carry the same manifest hash and release-set id or `initialize()` throws `ManifestMismatchError` (PRD §15.4) | T1.7, T3.11 (release-set pins), T1.17 | A consumer who edits their own local copy of the manifest disables their own protection; that is their build, and out of scope per §1.2 |

### 4.4 Hostile input at the FFI boundary

Everything crossing the Dart↔native boundary in either direction is untrusted. "Untrusted in both directions" is deliberate: a substituted library (TM-13) makes upstream's *outputs* an attack surface.

| # | Threat | Component | Mitigation | Owner | Residual risk |
|---|---|---|---|---|---|
| TM-17 | **Malformed lengths.** A length or size crossing FFI is negative, zero, larger than the buffer, or overflows when converted between Dart `int` and the native size type; a copy-out then reads out of bounds | wrappers, adapter | Every borrow-bytes path reads the length from the owning `TWData` object and validates it against a documented maximum before allocating or copying; sizes are checked for negativity and range at the wrapper boundary, not inside the call; property-generated and fuzzed lengths are part of the gate suite (PRD §16 S5) | T1.6 (wrappers), T2.12 (hostile-input suite), T1.13 (adapter, if chosen) | An out-of-bounds read *inside* upstream from a length we passed validly is upstream's defect (§1.2) |
| TM-18 | **Malformed protobuf input.** Bytes that do not parse, parse into a different message, or carry unexpected or oversized fields are handed to a signer — most plausibly through `RawSigningInput` under `advanced.dart` | signer, worker | `RawSigningInput` exists only under `advanced.dart`, where the caller accepts responsibility, precisely because arbitrary protobuf bytes can contain key fields and we cannot prove otherwise (PRD §10.2). The typed path never accepts caller-supplied protobuf bytes: family code builds the message from validated Dart values. Fuzzed protobuf payloads are in the gate suite | T1.12 / T2.0 (family encoders), T2.12, T3.3 (`advanced.dart` docs) | A caller using `advanced.dart` can do anything; that is the documented bargain |
| TM-19 | **Malformed native return values.** Upstream returns an unexpected enum value, an empty `TWData` where content is required, a truncated result, or a value inconsistent with the requested coin | wrappers, signer | Every return value is checked at the wrapper boundary before use; unknown enum values map to a typed error rather than a default case; empty or short results raise `SigningError` instead of being returned as a valid result. No result is ever returned to the caller unparsed | T1.6, T2.0, T2.12 | If a substituted library returns a *well-formed but wrong* signature, no amount of parsing detects it; the defense is TM-13/TM-14, not parsing |
| TM-20 | **Null pointers.** Upstream signals failure by returning `nullptr` (address parse, key creation, signer construction) and the wrapper dereferences it, crashing the process or worse | wrappers, worker, adapter | Every call site that can return a pointer checks for null before constructing a wrapper, and throws the mapped typed error (`InvalidInputError`, `KeyResolutionError`, `SigningError`); the check is generated or hand-written at the wrapper boundary, never left to the caller. Null-return paths appear in the hostile-input suite with a fault-injection seam | T1.6, T2.12, T1.13 (adapter) | A null in a path we did not anticipate crashes the worker isolate rather than the app — which is why TM-25 exists |
| TM-21 | **Input reaching native unvalidated.** A malformed address, derivation path, chain id, or an amount wider than the chain's integer width reaches native code and produces a signature over nonsense | signer, worker | Addresses, derivation paths, amounts, chain ids, and lengths are validated in Dart; invalid input raises `InvalidInputError` without reaching native code where feasible; wrong-network addresses and numeric-boundary cases are explicit test classes (PRD §16 S5) | T1.11 (validation), T2.0, T2.12 | Validation is per-family and only as complete as the family's rules; "exposed, unverified" coins get generic validation only |
| TM-22 | **Hostile `SigningOutput`** *(audit-derived)*. The output message a signer parses is attacker-influenced — from a substituted library, a corrupted artifact, or a hostile `advanced.dart` caller — and carries oversized fields, a populated `error`/`error_message` with a plausible-looking payload, or a shape that does not match the requested coin | signer | `parseSigningOutput` treats the output as untrusted: it checks `error`/`error_message` **first** and maps them to `SigningError(upstreamCode, message)` without interpreting the rest; field sizes are bounded before copy-out; the parsed result must match the requested coin family or the call fails; no output field is ever executed, formatted as code, or used to select a code path beyond the sealed `SignResult` variant | T2.0 (sealed results, parsing), T2.12 (hostile outputs in the suite) | A well-formed output containing a valid signature over a *different* payload is indistinguishable to us; only the byte-for-byte vector tests (T1.10, T2.2 … T2.4) and artifact integrity catch that class |

### 4.5 Worker, lifecycle, and request integrity

| # | Threat | Component | Mitigation | Owner | Residual risk |
|---|---|---|---|---|---|
| TM-23 | **A public proxy frees a worker-owned pointer** *(audit-derived)*. A public object in the UI isolate disposes a handle that lives in the worker — directly, or through a finalizer — producing a cross-isolate free, a double free, or a use-after-free in the worker | worker, wrappers | Public objects are proxies holding an opaque ref, never a `Pointer`; the public API exposes only an asynchronous, idempotent `close()` that posts `Dispose(ref)` to the worker and awaits the acknowledgement, while synchronous `dispose()` stays on internal handles inside the owning isolate (PRD §11.2, §14.3). A proxy attaches a **managed** Dart `Finalizer`, which can post `Dispose(ref)` to the worker; a `NativeFinalizer`, which cannot run Dart code, is never attached to a proxy. The worker treats a `Dispose` for an unknown or already-disposed ref as a no-op. `lint:public-api` keeps `dart:ffi` types out of public signatures so the mistake is not expressible | T0.11 / DECISION-12 (protocol), T1.11 (proxies), T2.1 (worker), T1.15 (lint), T1.6 (internal disposal) | Under `advanced.dart` the same-isolate `HDWallet` keeps the synchronous contract and *can* be misused; documented as the caller's responsibility (T3.3) |
| TM-24 | **A request carries key material by mistake** *(audit-derived)*. A private key ends up inside a `*TransactionRequest` — through a new family field, a caller-populated protobuf, or a signer path that skips the key-less encoder — and then crosses isolates, appears in logs, or is retained by the app | signer, worker, docs | Requests are key-less by construction (PRD §10.2). Family code implements `encodeKeylessInput(request)` and never receives key bytes; only the selected signer path injects keys, and before injecting it verifies against a **reviewed per-family list of key field names** that the key-less input contains none (PRD §11.4). The lists are part of the family code and reviewed when a family is added or an upstream proto changes; a test asserts the check fires for Bitcoin's `repeated bytes private_key` and Solana's three key fields. `RawSigningInput` lives only in `advanced.dart` | T2.0 (family boundary, key-field lists), T1.12 (EVM path), T2.12 (assertions), T0.11 / DECISION-13 | No generic detection is possible: upstream protos carry no secret marker, so the guarantee is exactly as good as the reviewed per-family list. A new upstream key field with a new name is missed until the API diff (T4.1) surfaces it |
| TM-25 | **Worker termination mid-request** *(audit-derived)*. The worker isolate dies — uncaught error, OOM, a native crash — while a request holding derived key material is in flight | worker | A *native* crash inside the worker terminates the whole process and is observable only by the app's platform crash reporter; `WorkerTerminatedError(kind)` covers a Dart uncaught error and an isolate exit (DECISION-12 §3.10). Every pending and queued operation is rejected with `WorkerTerminatedError(kind)`; nothing is retried silently, because a silent retry could re-derive keys or re-submit a transaction. All refs become invalid and the session moves to `failed`; recovery is an explicit re-initialization by the app. `shutdown()` is the graceful counterpart: stop accepting work, resolve or reject queued operations, dispose handles, detach finalizers, exit. Crash injection and shutdown-with-pending-work are gate tests (PRD §16 S5) | T2.1 (worker), T0.11 / DECISION-12, T2.12 (fault injection), T1.11 (session states) | On abrupt isolate death or process crash, native allocations owned by that isolate are not wiped — finalizers are not guaranteed on abnormal termination (PRD §11.1) — so key bytes may remain in the process's native heap until process exit |
| TM-26 | **Queue and timeout abuse.** Unbounded queuing, a request that never completes, or a cancellation racing a native call leaves operations and their key material pending indefinitely | worker | The queue is bounded and rejects with a typed error rather than growing; every operation carries a request id and a timeout; an operation can be cancelled before it starts, while one already in native code runs to completion and disposes its temporaries (PRD §14.3) | T2.1, T0.11 / DECISION-12, T2.12 | A single pathological native call still occupies the sequential worker for its duration; throughput is bounded by design (PRD §14.2) |

### 4.6 Supply chain, monitoring, and response

## 5. What we deliberately do not promise

These are limitations of the design, chosen knowingly and stated so that nobody builds on a guarantee that does not exist. They mirror PRD §11.3.

1. **We do not promise that every copy of a secret is erased.** When a wrapper is disposed, upstream wipes the buffer that object currently owns — that much is guaranteed. Beyond it, copies can exist in Dart heap objects (`Uint8List`, `String`, protobuf messages, serialized bytes), in earlier native allocations upstream reallocated internally, in the GC's copying and compaction history, in platform keyboard and clipboard buffers, in crash dumps, and in swap. Dart provides no API to pin or erase managed memory. Overwriting our own buffers narrows the window; it does not close it.
2. **We do not defend against a compromised host.** A rooted or jailbroken device, a hostile OS, an attached debugger, a malicious keyboard, or physical memory extraction defeats every mitigation in §4. The SDK's threat model assumes the device is honest.
3. **We do not promise that a mnemonic or passphrase the caller gave us, or that we returned, is gone.** Import accepts a `String`; export returns one. We drop our own references as soon as the native wallet exists. The caller's copy and the platform's copies are beyond reach.
4. **We do not claim upstream's security reviews cover this code.** Reviews of wallet-core say nothing about the FFI glue, protobuf construction in Dart, artifact acquisition, the loader, the worker, or the signer. An external review of the glue layer is scoped separately (PRD §16 S6, T5.8) and its findings will be recorded, not summarized away.
5. **We do not promise that an independent rebuild of the native artifacts yields byte-identical output.** Checksum verification against the manifest is required from M0 and is what integrity currently rests on; independent-rebuild verification is a separate, later requirement (PRD §12.4, T4.4) whose outcome depends on upstream's build determinism, which we do not control. Until it is demonstrated, the documentation says "checksum-pinned" and nothing stronger.
6. **We do not promise per-coin correctness beyond the tested vectors.** "Exposed" is not "verified". The capability matrix names the exact variants proven by a vector; everything else is labeled exposed-unverified, and signing an unverified variant is the caller's risk.
7. **We ship no storage, no lock timer, no UI protection, and no key backup.** The app owns all of them; §4.2 says which.

## 6. Open questions

### For T0.11 (DECISION-12, DECISION-13)

1. **DECISION-12 — proxy disposal.** Is the managed Dart `Finalizer` on a public proxy allowed to post `Dispose(ref)` after the session has already moved to `closing`/`closed`, and what does the worker do with a `Dispose` that arrives after `Shutdown`? TM-23 assumes an unknown-ref no-op; the protocol must say so explicitly.
2. **DECISION-12 — in-flight close.** When `close()` arrives during an in-flight operation on the same handle, the operation completes first (PRD §14.3). Does the key material derived for that operation get disposed before or after the acknowledgement is sent? TM-01's residence-time claim depends on the answer.
3. **DECISION-12 — failure taxonomy.** Should a *native* crash inside the worker be distinguishable from a Dart uncaught error at the API level? TM-25 currently maps both to `WorkerTerminatedError`; a security-relevant crash may deserve a distinct signal for the app's own reporting. *Answered in v0.1: DECISION-12 §3.10 — a native crash ends the process and has no kind; TM-25 updated.*
4. **DECISION-13 — key-field lists.** Where do the per-family key field-name lists live, and what forces them to be re-reviewed when upstream adds a field? TM-24's residual risk is bounded only by that mechanism. A candidate is a check in the API diff (T4.1) that fails when a proto gains a field whose name matches a key-like pattern and that is not in the list.
5. **DECISION-13 — `KeyLocator` scope.** Can a `KeyLocator` name a key in a *different* wallet or session than the one the request is signed against, and if so, what prevents a request from being signed with an unintended key set? TM-24 covers keys inside the request; this is the complementary question about keys named beside it.
6. **DECISION-13 — external signers.** For a future `ExternalSigner`, which parts of §4 change owner? An external signer never touches the worker, so TM-01, TM-23, and TM-25 do not apply, but a new class of threats (transport to the device, user confirmation on a small screen) appears. v0 does not model it; DECISION-13 should say whether v1 of this document must.

### For D0

7. **Upstream advisory monitoring (TM-27).** The watcher is release-triggered. Do we also need an advisory or master-branch subscription, and who owns it? No task currently does. *Answered in v0.1: T4.3 polls the repository security-advisories feed (TM-27); untagged master fixes remain a residual risk.*
8. **pub-ecosystem dependency monitoring (TM-28).** Dependabot covers GitHub Actions only. Adding `package-ecosystem: pub` is a small change with an owner to assign — T0.2's scope, extended, or a Phase 1 task. *Answered in v0.1: T1.17 (TM-28).*
9. **DECISION-1's effect on this model.** Approach B removes the private key from Dart memory (TM-01's residual risk) but adds the adapter as a reviewed component with its own memory-safety surface (TM-17, TM-20) and a per-family key-insertion path that TM-24 must then cover in C as well as Dart. Whichever way DECISION-1 goes, one column of this table changes; D0 should note which.
10. **Scope of the external review (DECISION-4).** §1.1 lists the components; the review scope pack is T5.8. Whether the adapter exists is DECISION-1's output, so the review's scope cannot be fixed before M0 exit.

### Could not be modeled without code

- Actual key residence times, allocation counts, and the number of Dart-side copies of a serialized signing input (TM-01). These are measurements, not design facts; T1.12 and T2.10 produce them.
- The concrete null-return and error-code behavior of upstream per coin (TM-19, TM-20). The probes (T1.14, T2.9) and the hostile-input suite (T2.12) supply it.
- Whether `TWAnySignerSignJSON` is available for enough coins to matter as a key-handling path (PRD §11.1). T1.14 measures it.
