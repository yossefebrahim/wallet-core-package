## 1. What Option 1 is, as built

**The hook.** `packages/wallet_core_flutter_native/hook/build.dart`, invoked by Flutter once per target OS, architecture and — on iOS — SDK:

1. **Selects** the manifest artifact for the target (`hook/src/targets.dart`): Android `android/<abi>/libTrustWalletCore.so` for `arm64-v8a` and `x86_64` (`armeabi-v7a`, x86 and RISC-V fail the build before any manifest lookup, naming the shipped ABIs, PRD §12.2 step 8 and the `--target-platform android-arm64,android-x64` remedy — §13); iOS device `ios/arm64/libTrustWalletCore.dylib`; iOS simulator `ios-simulator/<arch>/…` if listed, else `ios-simulator/arm64_x86_64/…`; macOS likewise. Linux and Windows get no asset and no failure.
2. **Obtains it verified, twice** (`hook/src/acquire.dart`). First it calls T1.7b's `runFetchArtifacts` with `--only <logical name> --manifest … --cache-dir …` and an **empty environment**: the fetch tool re-hashes a cache entry, verifies a vendored file before copying it, verifies a download before renaming it into place, checks sha256 **and** size, and has no path that accepts a mismatch. Then the hook reads the cache file **once** and hashes those bytes against the sha256 and size it parsed from the manifest itself; only those in-memory bytes are sliced and bundled, and the cache path is never opened again. The second check exists because the fetch tool's verdict is about the file as it was when it hashed it: the cache path carries no set id, so a `cache_dir` shared between apps that pin different manifests — or any other local writer — could replace the file between that verdict and the read, and the first version of the hook would have bundled the replacement under a log line naming the pinned digest (review finding 1, reproduced in `test/hook/acquire_test.dart`). A failure at either check fails the build with the artifact, the expected and the found sha256 and size, what to do, and the command that reproduces it outside the build (§3 shows the real text).
3. **Takes the slice** (`hook/src/slices.dart`): Flutter runs `lipo -create` over the per-architecture files of one asset id, so a universal artifact emitted unchanged for both the arm64 and the x86_64 invocation would make that `lipo` fail. The hook emits the target's slice — a byte range of the verified bytes, nothing relinked or re-signed. On the real macOS dylib the emitted arm64 slice is **byte-identical to `lipo -thin arm64`** (measured; also a test). A thin artifact is checked to *be* the target architecture, and an Android `.so` to carry the ABI's ELF machine, so a manifest that files a library under the wrong slice fails at build time.
4. **Emits one `CodeAsset`**: id `package:wallet_core_flutter_native/wallet_core`, `DynamicLoadingBundled()`, file `libTrustWalletCore.dylib` on every Apple target and `libTrustWalletCore.so` on every Android ABI — the same id and name across device, simulator and architecture (PRD §12.1, iOS row; tested).

**Configuration** comes from the consuming app's `pubspec.yaml`, because hooks run with a filtered environment (`hooks_runner` — 1.1.1 in Flutter 3.44.1, 1.5.0 in 3.47.5 — starts them with `includeParentEnvironment: false`; `WCF_ARTIFACT_DIR` never reaches a hook):

```yaml
hooks:
  user_defines:
    wallet_core_flutter_native:
      offline: true            # never download: cache or vendored only
      vendored_dir: <dir>      # laid out by logical name
      cache_dir: <dir>         # default: the hook's own shared output dir, per app
      manifest: <path>         # replace the shipped manifest
```

An unknown key fails the build (a typo must not silently re-enable the network). None of these is visible at run time, which is what TM-13 asks of a vendored directory.

**Network rule (one rule).** The hook **may download**, and only like this: when neither the verified cache nor the vendored directory holds the artifact, from the manifest's own DECISION-14 §3.1 content-addressed URLs (`retention.primary`, then `retention.mirror` when non-null), over HTTPS only, through the fetch tool's code, verified before use. `offline: true` removes the network entirely. Reason: PRD §12.3 puts the fetch "at consumer build time by the native package", §16 S4 allows build-time network in the hook, and step 7 measures "no network access *except* the artifact fetch". The alternative — the hook never downloads and the consumer pre-populates a cache with `dart run wallet_core_flutter_native:fetch_artifacts` — was rejected because it adds a manual step to every consumer build, which step 1 forbids. Since `main` f9f3d58 the root manifest pins `as_4.8.0_001` and `retention.primary` names the release `native-4.8.0-001`. That release is still a **draft**, whose assets answer anonymous requests with HTTP 404, so a build that has to download fails until it is published (§13 item 4); every build in this evaluation is `offline: true` from the vendored copy.

**Where the loader finds it.** `lib/src/code_asset_locations.dart` adds `codeAssetLocations(platform:)` and nothing else: Android `NamedLibrary('libTrustWalletCore.so')`; iOS `NamedLibrary('TrustWalletCore.framework/TrustWalletCore')` (the existing `iosFrameworkLibraryPath` constant); macOS the **absolute** path `<App>.app/Contents/Frameworks/TrustWalletCore.framework/TrustWalletCore`, derived from the running executable (§7). `loader.dart`, `library_location.dart` and the default list are unchanged. §7 explains why the default list is not enough and why macOS does not use the relative name.

**`libc++_shared.so`.** `android_libcpp_shared` 0.2.1 as a dependency — §5, and its open item §5.1.

**Not built:** an `@Native`/asset-id route (§7), any Podfile, Gradle or Xcode change, any network fetch in this evaluation (every build here is `offline: true` from `third_party/wcf-native-all/artifacts`).

## 5. `libc++_shared.so`

`libc++_shared.so` is not a system library on Android; a library that uses the shared C++ runtime must bring it. The Flutter docs (PRD §12.1, Android row) point to `package:android_libcpp_shared`, and the native package depends on it (0.2.1). Its hook is a no-op off Android; on Android it emits `libc++_shared.so` as a `DynamicLoadingBundled` code asset under **one** asset id, `package:android_libcpp_shared/libc++_shared.so`, taken from the NDK the Flutter build uses (0.2.1 derives it from the compiler in the hook input; the default NDK of Flutter 3.44.1 and of 3.47.5 is 28.2.13676358, which `run_eval.sh` reads from the installed Flutter's Gradle plugin) and falling back to other installations. Every hook-based package that depends on it therefore dedupes to one copy.

### 5.1 Open item — the file is not digest-pinned (review finding 6)

> **For the repository owner to decide; the evaluation does not change the dependency.**
>
> **What:** `packages/wallet_core_flutter_native/pubspec.yaml` depends on `android_libcpp_shared: ^0.2.0` (resolved 0.2.1). Its build hook runs in **every** consumer build and, on Android, bundles a `libc++_shared.so` from whichever NDK it finds (the build's own, else another installation). **No sha256 is checked anywhere on that path.** That contradicts PRD §12.3 ("every artifact's SHA-256 is pinned"): it is the one native file an Option 1 app ships that no manifest digest covers. Option 2 pins the same file as a manifest row instead.
>
> **Reviewer's evidence:** CONFIRMED by reading — no digest check on that path. PLAUSIBLE, not confirmed: an environment-variable path override inside that package (the reviewer's pub-cache reads became permission-gated before it could be confirmed). Its hook has no network code (checked).
>
> **Options:**
> 1. **Drop the dependency until T1.2 settles `c++_static` vs `c++_shared`.** With `c++_static` our `.so` needs no `libc++_shared.so` at all; `llvm-readelf -d` (DT_NEEDED) on the first Android artifact answers it. Until an Android artifact exists the dependency bundles nothing our library needs, but it still runs in every Android consumer build.
> 2. **If shared, ship `libc++_shared.so` as a verified manifest row through this package's own hook** — sha256 and size like every other artifact, bundled as a second `CodeAsset` — and drop `android_libcpp_shared`. That loses the one-asset-id dedupe across hook-based packages (step 9's question then becomes ours alone).

**Answered with data (T1.8b, 2026-10-04, `run_eval.sh` step 9 and the step 1 APKs):**

- **Our library does not need `libc++_shared.so`.** `llvm-readelf -d` on both shipped `.so` of `as_4.8.0_001`: `DT_NEEDED` is `liblog.so libm.so libdl.so libc.so` and nothing else — the C++ runtime is linked statically.
- **Every Android app still ships one, unpinned.** Each APK of step 1 carries `lib/arm64-v8a/libc++_shared.so` (1 253 544 B) and `lib/x86_64/libc++_shared.so` (1 229 808 B) from `android_libcpp_shared` — NDK 28.2.13676358's copy by GNU build ID — 2.37 MiB of the 45.41 MiB APK delta, loaded by nothing of ours, and covered by no digest.
- **Next to a plugin that bundles its own** (the fixture, NDK 28.0.12674087's copy): no duplicate-file failure, no Gradle message, no `pickFirsts` rule needed; one copy per ABI is packaged — `android_libcpp_shared`'s, the app module's native-assets copy — and the plugin's is dropped silently. The release probe passes on the emulator with both plugins present.
- **So option 1 above is supported by the data:** dropping the dependency removes an unpinned file, 2.37 MiB per app and a third-party build-time hook, and changes nothing our library loads; it would also stop our package from silently replacing another plugin's `libc++_shared.so` with a different NDK's (§13 item 3). Option 2 applies only if a future set switches to `c++_shared`. The decision stays the owner's: `pubspec.yaml` is not changed here.
- **Supply chain.** A third-party package whose hook runs in every consumer build, on every platform (as a no-op off Android). It reads environment-derived NDK locations and the hook input; it does not download.
- The NDK's file is 16 KB aligned (measured on 28.2.13676358, arm64-v8a and x86_64), and so is every `.so` entry of the APKs that carry it (step 8).

## 6. Static vs dynamic, signing, privacy manifest

- **`DynamicLoadingBundled` accepts our dylib.** On the host, Flutter took the emitted slice, rewrote its install name, re-signed it and mapped the asset id to it in `native_assets.json`; the probe loaded it, read `wcf_build_info`, resolved all 467 names and called `TWAnyAddressIsValid` correctly (measured). For apps, `flutter_tools` wraps each dylib in `<name>.framework` (`libTrustWalletCore.dylib` → `TrustWalletCore.framework/TrustWalletCore`), sets the install name to `@rpath/TrustWalletCore.framework/TrustWalletCore`, writes an `Info.plist`, and embeds it in the app's `Frameworks/`. The framework is **embedded, not linked**: the Runner has no load command for it, and it is opened by `dlopen` at first use.
- **Static linking is not available.** `code_assets` 1.2.1 has `StaticLinking` with `// TODO(…): Support static linking`, and Flutter always asks for dynamic. The hook refuses a static-only preference with a message.
- **Header padding — a defect in our artifacts that this option exposes.** Flutter rewrites the install name of every bundled dylib (`install_name_tool -id`). Our dylibs were linked without `-headerpad_max_install_names`; the space left after their load commands is 56 bytes (macOS arm64), 104 (macOS x86_64), 104 (simulator arm64), 88 (simulator x86_64) and 13 920 (device arm64) — `otool -l` `sizeofcmds` + 32 against the `__text` section offset. The app-bundle name needs 24 more bytes and **fits every slice** (measured with `install_name_tool` on copies). Host `flutter test` instead uses the file's **absolute path**, which fits the macOS arm64 slice only up to 87 characters: in this repository's checkout (133 characters, measured on every run through 2026-10-02) it fails with "changing install names or rpaths can't be redone … larger updated load commands do not fit (the program must be relinked, and you may need to use -headerpad or -headerpad_max_install_names)"; from the short path it passes (78 characters on the 2026-10-02 run, 77 on 2026-10-01 — the pid's digit count) — the same on Flutter 3.44.1 and 3.47.5 (re-measured). **The default macOS temporary directory is already too deep:** `$TMPDIR` resolves to `/private/var/folders/…/T/`, which put the staged host test at 112 characters, and it failed the same way (2026-10-01 and 2026-10-02). `run_eval.sh` therefore runs the host test twice, from staged copies — under `$TMPDIR` and from `/tmp/wcf-o1-<pid>` (resolved `/private/tmp/wcf-o1-<pid>/h/…`: 73 characters plus the pid's digits, 74–78, created and removed by the script) — and records each against the 87-character limit; neither stops the run. The in-place run was dropped in delta 5: it added only another length above the limit, and running anything in the checkout writes a Podfile into it (§12). Because every `flutter test` on a Mac runs this hook (next point), **a consumer's unit tests would fail on a Mac in any normally deep project directory** whenever the manifest ships a macOS library. Fix: T1.2 links every Apple artifact with `-Wl,-headerpad_max_install_names`. **Fixed in T1.2-d1 (2026-10-03, `integration/W5`):** the link line now carries the flag; verified on the host build (`install_name_tool -id` with a 213-byte id accepted). **Re-measured on `as_4.8.0_001` (2026-10-04):** the macOS arm64 slice now has 6 168 spare header bytes (`otool -l`: `__text` at offset 8 480, `sizeofcmds` 2 280), an install-name limit of 6 199 characters, and both host tests pass (112 and 78 characters); the numbers above are `as_4.8.0_000`'s.
- **Every `flutter test` runs the hook on the host.** Not only in apps: `melos run test` in this repository runs `wallet_core_flutter_native`'s own hook for macOS, and failed outright before macOS was made optional, because the shipped manifest has no macOS artifact. macOS is therefore best-effort in the hook — no macOS artifact in the manifest means no asset, a listed one is verified like any other — while Android and iOS stay strict.
- **Code signing.** Flutter signs each embedded framework itself during the Xcode build (`codesign --force --sign <identity or ->`, `--timestamp=none` outside release), so our unsigned device dylib is fine and §12.2 step 10's "sign the xcframework" has no object under this option — there is no xcframework. The App Store export re-signs as for any embedded framework (T1.8b to confirm on a signed archive).
- **Deployment targets.** Flutter 3.47.5 writes `MinimumOSVersion` 15.0 into every native-asset framework (3.44.1 wrote 13.0, below our simulator arm64 slice's 14.0); all our iOS slices (device 13.0, simulator 14.0 / 13.0) are at or below it, so on 3.47.5 there is no mismatch. Our macOS slices say **26.0** — the library will not load on an older macOS host; T1.2 should set the macOS deployment target to the Flutter template's (12.0 on 3.47.5) if macOS stays a test host.
- **`PrivacyInfo.xcprivacy`.** Every slice imports APIs from two required-reason categories, so the app needs a privacy manifest declaring both. Under Option 1 **the package has no channel to ship one**: a `CodeAsset` is a single file, and the framework Flutter generates holds only `Info.plist`, the binary and `_CodeSignature` — measured in the release archive of the 2026-10-01 and 2026-10-02 runs (`TrustWalletCore.framework holds: Info.plist TrustWalletCore _CodeSignature; no PrivacyInfo.xcprivacy in the framework`); `data_assets` land in `flutter_assets`, not in the framework. The declaration must therefore live in the **app's** `ios/Runner/PrivacyInfo.xcprivacy`, added to the Runner target in Xcode — a manual native edit by the consumer, which step 1 rules out. The `ios-archive-link` row records the framework's contents on every run.

## 7. How the loader finds the asset — consequences for T1.7 and the bindings

- **The default iOS list does not work under this option.** `defaultLocations(platform: ios)` tries `ProcessLibrary` first, and `DynamicLibrary.process()` never fails. The hook-bundled framework is embedded but not linked, so the process "opens", has no `wcf_build_info`, and the framework entry after it is never reached: the load succeeds with the wrong image and the identity check fails. On macOS the default name `libTrustWalletCore.dylib` is not where the framework is. `codeAssetLocations` fixes both by listing only the framework (and never the process), without touching the loader. If Option 1 wins, T1.7's default list should become option-aware rather than order-dependent.
- **macOS: an absolute path, never a working-directory-relative one** (review finding 15, TM-13). A relative path containing a slash, such as `TrustWalletCore.framework/TrustWalletCore`, is a path to `dlopen`, and dyld tries it against the current working directory — on a Mac whatever directory the app was started from, often writable by the user. The hooks API offers nothing better: the asset id resolves only for `@Native` declarations (next point), and no API returns the path Flutter recorded for it. So `codeAssetLocations` derives the location from the running executable (`Platform.resolvedExecutable`), which a macOS bundle keeps at `<App>.app/Contents/MacOS/<name>`: the framework is `<App>.app/Contents/Frameworks/TrustWalletCore.framework/TrustWalletCore`, opened as an absolute `LibraryFile`. An executable that is not absolute or not in a bundle's `Contents/MacOS/` yields no location rather than a guess (tested). The host `flutter test` route does not use this list: it opens the absolute path recorded in `build/native_assets/macos/native_assets.json`. Not yet measured in a running macOS app — the macOS desktop app does not build on this host (§10) — so the `run-on-target macos-host/debug` row is where it will show.
- **iOS keeps the framework-relative name, and why that is safe enough to leave.** An iOS app starts with the working directory `/`, on the read-only system volume and outside the app's sandbox, so the relative candidate names a file no app or user can place; the framework then resolves through the app's own `@rpath` (`@executable_path/Frameworks`). That is an argument from where the process starts, not a measured property of dyld's search order; the simulator runs of 2026-10-01 and 2026-10-02 (the latter on an iPhone 17 simulator, iOS 26.5) loaded the right image through it — identity `as_4.8.0_000` @ `d692ac2…`, 467 names resolved, `TWAnyAddressIsValid` correct — and so did the 2026-10-04 run on an iPhone 16 Pro simulator (iOS 18.0) with `as_4.8.0_001`. On Android, `NamedLibrary('libTrustWalletCore.so')` resolved the hook-bundled `.so` on the arm64-v8a emulator in debug and release (2026-10-04). Deriving the iOS path from the executable the same way (`<App>.app/Frameworks/…`) is a one-line change if D1a wants both platforms alike.
- **The framework path is a `flutter_tools` convention, not a protocol contract.** `frameworkUri` derives it from the file name and appends a number when two packages emit the same name (`TrustWalletCore1.framework`). Under `flutter test` there is no framework at all: the file sits at an absolute host path, recorded only in `build/native_assets/<os>/native_assets.json` (the host test reads that file).
- **The stable handle is the asset id, and only `@Native` can use it.** `dart:ffi` resolves `package:wallet_core_flutter_native/wallet_core` for `@Native(assetId: …)` declarations; there is no API that turns an asset id into a `DynamicLibrary`, which is what the generated `WalletCoreBindings` constructor takes. Moving to asset ids would mean regenerating the bindings in ffigen's `ffi-native` mode (static `@Native` functions, no `DynamicLibrary`), and the loader's `verifyIdentity(DynamicLibrary)` / `requireSymbols(DynamicLibrary, …)` would have to become `@Native` lookups or `Native.addressOf`. Not built here; the path-based location works today.

## 9. Risks

1. **Header padding** (§6) — fixed in `as_4.8.0_001` (re-measured 2026-10-04); keep the link flag in every future set.
2. **Privacy manifest** (§6) — Option 1 cannot ship it; every iOS consumer edits the Runner target.
3. **An unpinned Android library** (§5.1) — `android_libcpp_shared` bundles `libc++_shared.so` with no digest check into every APK, and our library does not use it (measured); open item for the repository owner.
4. **Tooling conventions as interface** (§7) — the framework path and the per-architecture `lipo` are `flutter_tools` behaviour, not the hooks protocol; a Flutter release can change them.
5. **Hook in every build and every test** — a defect in the hook, the manifest or the cache breaks `flutter test` for every consumer, including those that never load the library; the hook's failure messages are the only diagnostic.
6. **Third-party build-time code** — `android_libcpp_shared` runs in every consumer build.
7. **Download size per app** — ~20 MB per slice per app unless `cache_dir` is shared (§8).
8. **Draft release** — until `native-4.8.0-001` is published, every networked build and every networked host `flutter test` on a Mac fails at the download (§13 item 4).
9. **Untested floor** — Flutter 3.44.0 is what the package declares (and Dart 3.10 what its hooks dependencies would allow); 3.47.5 is what was built. The host Xcode, through the `flutter create` template's deployment targets, decides which older Flutter can be tried at all (§4).
10. **Default Android builds fail** (§13 item 1) — without `--target-platform android-arm64,android-x64`, `flutter build apk`/`appbundle` stop at the hook's `armeabi-v7a` refusal.
11. **Silent `libc++_shared.so` override** (§13 item 3) — another plugin's copy is replaced by `android_libcpp_shared`'s without a message.

## 13. Android findings (T1.8b, 2026-10-04)

Measured by `run_eval.sh` on the arm64-v8a emulator `emulator-5554` (AVD `wcf_api35`, API 35) with `as_4.8.0_001` vendored; every value is in §2.1 and its notes in `eval/option1/results/table.md`.

**What works, with no Gradle, manifest or project edit.** Debug and release APKs build with `--target-platform android-arm64,android-x64` and carry `lib/arm64-v8a/libTrustWalletCore.so` and `lib/x86_64/libTrustWalletCore.so` at their artifact sizes, bundled by the hook from `vendored_dir` with `offline: true` after an empty-cache start (one hook run per ABI). Both libraries export 464/464 `TW*` and `wcf_build_info` from `.dynsym`, have 16 KB `LOAD` alignment, and sit on 16 KB boundaries in both APKs. On the emulator the debug integration test and the release probe resolve all 467 names, report identity `as_4.8.0_001` @ `d692ac2…` and make a correct `TWAnyAddressIsValid` call; the release APK cold-starts and verifies with `apksigner` (debug keystore, the template's default). A flipped `arm64-v8a` digest fails the Gradle build, and its output starts with the hook's one-line verdict showing both digests. The loader's `NamedLibrary('libTrustWalletCore.so')` needs nothing Option-1-specific on Android.

**What broke, and what was fixed.**

1. **Harness: 0 exports on a stripped `.so`.** `tools/packaging_eval`'s `symbols.dart` went through this branch's `check_exports.sh`, which runs `llvm-nm` without `--dynamic` (the gate gained it on `main` in 56560e8). On the stripped release `.so` llvm-nm then reads `.symtab`, prints `no symbols`, and the row read `fail 0/464 TW*, 0 defined external, wcf_build_info no`. ELF is now read from `.dynsym` directly: `llvm-nm --dynamic --defined-only --extern-only` from the NDK, reconciled by `parseElfDynamicExports`, with `--allow-extra` for upstream's four JNI-glue exports. Test: `tools/packaging_eval/test/elf_symbols_test.dart`, against real output of both commands (`fixtures/tool_output/llvm_nm_*`). The change is self-contained under `tools/packaging_eval/` and belongs on `main` too.
2. **Hook: `armeabi-v7a`.** `as_4.8.0_001` ships no `armeabi-v7a` library. Under the T1.8a mapping a build that targets `android-arm` — every default `flutter build apk` or `appbundle` — failed at the manifest lookup with a message about per-slice artifacts and `.xcframework.zip`. The mapping is gone, so `android-arm` is refused before any lookup, like x86 and RISC-V. The message names the shipped ABIs, PRD §12.2 step 8, and the remedy `--target-platform android-arm64,android-x64`. The T1.8b draft's message recommended `android.defaultConfig.ndk.abiFilters` instead, and that **does not work**. Measured on a scratch staged copy with `ndk { abiFilters += listOf("arm64-v8a", "x86_64") }` in `android/app/build.gradle.kts`: `flutter build apk --debug` still ran the hook for `android-arm` and failed the same way, because Flutter derives the hook targets from its own target platforms. Test: `targets_test.dart` "armeabi-v7a is refused with the remedy, before any lookup". `BuildError` is a clean build failure, but Flutter prints the hooks runner's stack trace after the message.
3. **Evaluation script.** Every Android row of T1.8a was `unmeasured no artifact`. The script now builds, installs, runs and measures as §3 says. It measures packaged libraries from copies of the APKs taken right after their builds: step 2's `flutter test -d <emulator>` rebuilds the debug APK for one ABI, and the release probe rebuilds the release APK. It also records the default-ABI refusal. Step 9 uses a copy of the fixture with a second NDK's `libc++_shared.so`, outside the checkout. Parts of the T1.8b draft were replaced: the fixture had been added under the name `android_libcpp_shared` and without the hook's `user_defines`; the release run started `flutter run` in the background and killed it; packaged libraries were read from Gradle intermediates that later builds overwrite; and a `DT_NEEDED` row marked the absence of `libc++_shared.so` a `fail`.

**Residual risks and consumer costs.**

1. **A default Android build fails.** `flutter build apk` and `appbundle` without `--target-platform android-arm64,android-x64` stop at the hook (`consumer-build` / `android/armeabi-v7a`); `abiFilters` does not help. `flutter run` on a device is unaffected. D1a's options: build and test `armeabi-v7a` and ship it (PRD §12.2 step 8), or let the hook emit no asset for an unshipped ABI. The second keeps default builds green, but the app then fails at load on a 32-bit-only device. Not changed here.
2. **`libc++_shared.so`** — unpinned, 2.37 MiB per app, unused by our library (§5.1).
3. **Silent override of another plugin's `libc++_shared.so`.** With the fixture, the plugin's NDK 28.0 copy was replaced by `android_libcpp_shared`'s NDK 28.2 copy without a build message. That is harmless to us. It is a risk for a plugin built with a newer NDK than the one the app's build uses, because `libc++_shared.so` is compatible only with code built against the same or an older NDK. Dropping `android_libcpp_shared` (§5.1) removes our side of it.
4. **Draft release.** `native-4.8.0-001`'s assets return HTTP 404 anonymously. A consumer build that has to download fails until the release is published. So does this package's own `flutter test` on a Mac, which with the filled manifest now verifies, and so downloads, the macOS dylib: in T1.8b-d1's gate run it failed with `HTTP 404 Not Found` until the hook cache was pre-filled from the vendored copy.
5. **Not measured:** a run on an x86_64 emulator (Apple-Silicon host) and on a physical arm64 device; `flutter build appbundle` (AAB, the Play format; `alignment.dart` reads AABs, none was built); any Flutter other than 3.47.5.
