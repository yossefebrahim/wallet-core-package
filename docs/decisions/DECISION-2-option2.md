## 1. Option 2 as built

`packages/wallet_core_flutter_native` becomes an FFI plugin (`flutter: plugin: platforms: {android: {ffiPlugin: true}, ios: {ffiPlugin: true}}`). An FFI plugin has no method channel and no plugin class; the declarations only make Flutter's tooling include `android/` as a Gradle subproject and `ios/` as a CocoaPods pod of the consuming app. Nothing under `lib/` changed, and nothing in the fetch tool (`tool/fetch_artifacts.dart`, `tool/src/`): both platform integrations **call** it (in process, through its `runFetchArtifacts`), so every byte the build consumes passes the tool's sha256-and-size check, with no flag that accepts a mismatch (TM-14).

**Where the build-time Dart lives: `tool/option2/`**, not under `android/` or `ios/`. `prepare_jni_libs.dart`, `prepare_xcframework.dart`, and `src/{jni_libs_plan,xcframework_plan,verified_acquisition}.dart` sit beside the fetch tool they call. The first version kept them in `android/tool/` and `ios/tool/`, with `verified_acquisition.dart` copied into both. But `flutter pub get` (Flutter 3.47.5) rewrites this package's `analysis_options.yaml` and adds `android/**` and `ios/**` to `analyzer.exclude`, so about 1,000 lines of build-time Dart dropped out of `melos run analyze` (review finding 10, measured by the orchestrator: delete the two lines, run `flutter pub get`, and they are back). Narrowing the excludes cannot hold against the tool; moving the code can. The options file is left exactly as the tool writes it — the tool keeps comments, so it carries one saying why. Both callers start from the package root (Gradle's `projectDir.parentFile`; the podspec's `File.expand_path('..', __dir__)`, see §1.3), so the shared file now exists once. `test/packaging/build_time_analysis_test.dart` fails if any Dart file appears under `android/` or `ios/`, if an exclude in the current options file covers a file under `tool/`, or if `dart analyze --fatal-infos tool` reports anything. It passes on the options file as `flutter pub get` leaves it, and fails on an injected unused import in `tool/option2/src/jni_libs_plan.dart`.

### 1.1 The shared step: two passes through the fetch tool

`tool/option2/src/verified_acquisition.dart`, used by both prepare scripts, runs the tool twice:

1. **Acquire** into the shared cache (`--cache-dir` → `$WCF_ARTIFACT_DIR` → `~/.cache/wallet_core_flutter/<tag>/`), from a warm cache, a `--vendored` directory, or the network, as the build-time inputs allow.
2. **Copy out** into a work directory that belongs to this run alone, with the shared cache as `--vendored` and `--offline`: the tool verifies each file before copying and again after.

The platform step then *renames* the verified file into place — no copy after the last verification. The alternative rejected was copying from the shared cache after pass 1, which leaves a window in which a directory other processes share can change between the check and the use.

The copy-out pass closes that window only if its work directory really is private. On Android it is: Gradle's per-task `temporaryDir`, inside the app's own build. On iOS it is not by location: `--work` (`<pod>/.wcf_work`) and `--out` (`<pod>/Frameworks`) sit in the pod directory, which every app using that copy of the package shares — for a hosted package, the pub-cache copy. The first version passed `.wcf_work` itself, and an independent review (T1.9a-d3, finding 2) showed with the real `acquireVerified` that two concurrent `pod install`s against different manifests let one run delete the other's freshly verified file as "corrupt", copy its own in, and the other run then renamed those bytes into its framework and stamped them with its own manifest's digest — so its script phase passed and it linked the other set. `prepare_xcframework.dart` now holds an exclusive lock on `<pod>/.wcf_work/.lock` for the whole verify-assemble-stamp step and gives the fetch passes a fresh `<pod>/.wcf_work/run-*` directory, removed when the run ends (a crashed run's is removed by the next run, under the lock). Regression tests in `test/packaging/prepare_test.dart` ("prepare_xcframework in a shared pod directory") fail on the first version: one plants another run's verified file in the shared `--work` and checks it survives; the other holds the lock from the test process and checks a second `prepare_xcframework.dart` process waits before it touches anything.

Build-time inputs are the same four names on both platforms (asserted by `test/packaging/static_consistency_test.dart`): `WCF_MANIFEST` (default: the shipped `assets/compat_manifest.json`), `WCF_VENDORED_DIR`, `WCF_OFFLINE=1`, `WCF_ARTIFACT_DIR`; Gradle also accepts them as `wcf.*` project properties. None is read at run time (TM-13).

### 1.2 Android — `android/build.gradle`

- A per-variant task `wcfPrepare<Variant>JniLibs` (a `DefaultTask` subclass declared in the build script, `ExecOperations` injected) runs `dart --packages=<app>/.dart_tool/package_config.json <package>/tool/option2/prepare_jni_libs.dart` with the Flutter SDK's `dart` (from the app's `local.properties`, else `FLUTTER_ROOT`).
- `prepare_jni_libs.dart` maps every manifest key `android/<abi>/<file>.so` to `<abi>/<file>.so` (`tool/option2/src/jni_libs_plan.dart`, pure, tested): **the manifest decides the ABI set**, so `armeabi-v7a` ships exactly when the manifest lists it, a `libc++_shared.so` row ships exactly when T1.2 lists one, an unknown ABI directory or an ABI without `libTrustWalletCore.so` is refused.
- The task's output directory is registered with `variant.sources.jniLibs.addGeneratedSourceDirectory(task) { it.outputDir }`, which both places the libraries under `build/generated/` (never `src/main/jniLibs`) and wires the dependency so `merge<Variant>JniLibFolders` runs after it. The Variant API declares `sources.jniLibs` nullable; a variant without it fails the build with a `GradleException` rather than building an app with no native library (the first version's `jniLibs?.` skipped the wiring silently — review finding 13; pinned by `test/packaging/static_consistency_test.dart`). Rejected: `sourceSets.main.jniLibs.srcDir(...)` plus `tasks.matching { merge*JniLibFolders }.dependsOn(...)`, which works but leaves every other consumer of the source set (lint models) without a declared producer, the case Gradle 8+ reports as an implicit dependency.
- A non-zero tool exit becomes a `GradleException` carrying the command and the tool's full report — the build fails loudly (step 7).
- `packaging.jniLibs.useLegacyPackaging = false` (16 KB, step 8), with the caveat in §5.2.
- No CMake or ndk-build step: the libraries are prebuilt and checksum-pinned.

**Not run.** No Android artifact exists, and the sandbox reaches neither Maven nor Google's repository, so no Gradle build has executed this file. Its own `buildscript` classpath (AGP 9.0.1, from the 3.44.1 `plugin_ffi` template) is used only when the module is built on its own; inside an app the app's AGP applies — 9.1.0 / Gradle 9.3.1 in the 3.47.5 app template, unexercised here; its Dart half is tested with fakes (`test/packaging/prepare_test.dart`: layout, stale-ABI removal, a wrong byte → exit 1 with nothing packaged, the shipped placeholder manifest → exit 2).

### 1.3 iOS — `ios/wallet_core_flutter_native.podspec`

- **Where the xcframework is produced: while CocoaPods evaluates the podspec during `pod install`.** Flutter adds every plugin pod as `pod '<name>', :path => '.symlinks/plugins/<name>/ios'`, and CocoaPods does not run `prepare_command` for a path pod, so `prepare_command` was rejected. A build-time script phase was rejected as the *producer* because CocoaPods reads the xcframework's `Info.plist` at install time to generate the `[CP] Copy XCFrameworks` phase; a framework that appears only at build time is never integrated. Evaluation is the one hook that runs before that read. The podspec runs `tool/option2/prepare_xcframework.dart`; a failure raises `Pod::Informative`, and `pod install` fails with the fetch tool's report.
- **How the podspec reaches `../tool`.** Flutter's podhelper makes `<app>/ios/.symlinks/plugins/<name>` a symlink to the package root — the pub-cache copy for a hosted package, the package directory for a path dependency — and declares the pod `:path => '.symlinks/plugins/<name>/ios'`. CocoaPods neither copies nor re-links a `:path` (development) pod: it evaluates the podspec and builds from that directory in place, which is also why `prepare_command` never runs. So `__dir__` is `.symlinks/plugins/<name>/ios`, and the lexical `File.expand_path('..', __dir__)` is `.symlinks/plugins/<name>`, the symlink to the package root. `tool/` and `assets/` resolve through it. Had CocoaPods resolved the symlink first, `__dir__` would be `<package root>/ios` and `..` the same root: the link points at the package root, not at `ios/`, so both readings agree. The script phase's `${PODS_TARGET_SRCROOT}/..` is resolved by the kernel through the same link to the same root. `tool/` is a normal package directory; no `.gitignore` rule matches it (`git check-ignore`) and the package has no `.pubignore`, so pub puts it in a hosted package's archive. The fetch tool the build already depended on lives there too. Step 11 does not list the archive's `tool/` entries; that is unverified. The podspec's `preserve_paths` no longer lists a pod-local `tool/`; a `:path` pod is never cleaned, and a pattern outside the pod root could not be listed anyway. Read from Flutter's and CocoaPods' behaviour, not from their source in this session. Exercised by the orchestrator's run of 2026-10-02: `pod install` ran `tool/option2/prepare_xcframework.dart` through `.symlinks/plugins/wallet_core_flutter_native`, and the Xcode script phase found `../assets/compat_manifest.json`. A wrong path would have failed `pod install` loudly (the Dart script does not exist → non-zero exit → `Pod::Informative`).
- `prepare_xcframework.dart` understands two manifest shapes (`tool/option2/src/xcframework_plan.dart`, pure, tested):

  | Manifest rows | What happens |
  |---|---|
  | `ios/TrustWalletCore.xcframework.zip` (the root manifest's row) | verify, `ditto -x -k`, vendor as shipped — signature untouched |
  | `ios/<abi>/` + `ios-simulator/<abi>/libTrustWalletCore.dylib` (the local set) | verify, assemble — §6 |

  The zip row wins whenever it is listed, placeholder or not, so a manifest that names a CI xcframework can never silently fall back to assembling something else.
- `s.vendored_frameworks = 'Frameworks/TrustWalletCore.xcframework'`; `s.platform = :ios, '15.0'` — **fixed, not derived**, and deliberately not the library's own minimum. The device dylib's measured minimum is iOS 13.0 (`LC_BUILD_VERSION minos 13.0`; manifest `min_os: "13.0"`, still recorded in the framework's `Info.plist` and in the `ios-archive` rows), but Xcode 27's iphoneos SDK accepts 15.0–27.0 only and Flutter 3.47.5's own `Flutter.framework` declares `MinimumOSVersion 15.0` (both read at run time into the `host/xcode` row), so no app this pod can belong to targets less. Deriving the value at `pod install` — from the host SDK's `SDKSettings.plist`, or from the manifest — was rejected: it would make the spec, and `Podfile.lock`'s checksum of it, differ by machine, and on an older Xcode could declare less than Flutter itself supports. Measured: after `pod install`, all 18 `IPHONEOS_DEPLOYMENT_TARGET` settings in the Pods project are 15.0. The prepare step still refuses a manifest whose device slice needs a newer iOS than the pod declares; one C translation unit in `Classes/` so CocoaPods builds a target for the pod (the target carries the privacy bundle and the script phase); **no linker flags** — no `-all_load`, no `-force_load`, no `user_target_xcconfig`.
- `s.resource_bundles = { 'wallet_core_flutter_native_privacy' => ['Resources/PrivacyInfo.xcprivacy'] }`, declaring the two measured required-reason categories: file timestamp (`stat`, `fstat`, `lstat`, `fstatat`; reason `C617.1`) and system boot time (`mach_absolute_time`; reason `35F9.1`). The same file is also placed at the root of each framework bundle, where Apple's guidance puts a framework's manifest. The reasons are inferred from the imported symbols, not from a review of every upstream call site.
- A `[CP-User] Verify TrustWalletCore.xcframework against the manifest` script phase (`before_compile`, `always_out_of_date`) re-checks, on every Xcode build, that the manifest in effect is the one the xcframework was verified against (`wcf_manifest.sha256`) and that no framework binary changed since (`shasum -c wcf_binaries.sha256`). This closes the gap a podspec-time check leaves open: Flutter re-runs `pod install` only when the Podfile or plugin set changes, not when a manifest does. The check is only as good as the stamps: they describe the set the stamping run verified because the prepare step is serialized by its lock (§1.1). It runs once, before compiling; a replacement of `Frameworks/` by another app's `pod install` after it ran and before this build links and embeds the framework is not seen. Observed (orchestrator-runs, 2026-10-01 and again 2026-10-02, same digests): a build with the flipped manifest after a good `pod install` failed in this phase — `Error (Xcode): wallet_core_flutter_native: …eval_manifest.flipped.json (sha256 b2e14566…) is not the manifest TrustWalletCore.xcframework was verified against at pod install (sha256 143dcf99…); run pod install` — not by a re-run `pod install`. User-script sandboxing is off for this pod's target only (`ENABLE_USER_SCRIPT_SANDBOXING = NO`), because the phase reads the manifest outside the build products.
- Outside a Flutter app (`pod lib lint`, `pod ipc spec`) there is no package configuration to run the tool with; the podspec warns and evaluates without the side effect. `pod lib lint --quick` passes with one warning (`:path` source, identical to Flutter's own template).

### 1.4 Which `LibraryLocation` resolves

No new location and no change to `lib/`.

- **iOS: `ProcessLibrary()`, the first default — observed at run time** (orchestrator-runs, 2026-10-01 and 2026-10-02, iPhone 17 simulator, iOS 26.5, debug). The integration test's `run-on-target` / `symbols-runtime-lookup` values: `location_1` "the running process (statically linked or already-loaded image): opens, provides wcf_build_info"; `location_2` "loader search path for "TrustWalletCore.framework/TrustWalletCore": opens, provides wcf_build_info"; `resolved_by` the running process. Both defaults work; the first one wins. Why: `pod install` writes `-framework "TrustWalletCore"` into the app's link and embeds the framework (`pod-integration` row), so the app image carries a load command for `@rpath/TrustWalletCore.framework/TrustWalletCore` and dyld loads it at launch, before Dart runs. In a **release** build that load command is in `Runner` itself; in a **debug** build it is in `Runner.debug.dylib`, because Xcode's debug builds make `Runner` a stub that loads the app's code from that dylib — read from the orchestrator's built apps with `otool -L` (`Runner`: 0, `Runner.debug.dylib`: present, for both debug builds; `Runner`: present for the release archive). `run_eval.sh` inspects both images and records which one carries the load command in each `consumer-build` row (`load_command_trustwalletcore`). The 2026-10-02 run recorded `yes (Runner.debug.dylib)` for both debug builds and `yes (Runner)` for the release archive.
- **Android: `NamedLibrary('libTrustWalletCore.so')`, the only default.** AGP packages `<abi>/libTrustWalletCore.so` as `lib/<abi>/libTrustWalletCore.so` in the APK, which is on the app's native library search path. Waiting for an artifact (T1.9b).

## 5. `libc++_shared.so`

### 5.1 Bundling

The library is not a system library on Android; an artifact built against `c++_shared` must ship it. Option 2 bundles **exactly the copy the manifest lists**, as an `android/<abi>/libc++_shared.so` row verified like any other artifact, so the runtime that ships is the one the CI NDK linked against, not whatever NDK the consumer happens to have. The root manifest lists no such row today; the prepare step prints, per ABI, when a `libTrustWalletCore.so` row has no runtime row beside it ("correct for a `c++_static` artifact, a load failure on that ABI for a `c++_shared` one"), because only the artifact (`DT_NEEDED`) can say which it is. The rejected alternative — copying `libc++_shared.so` out of the consumer's NDK at build time — is not checksum-pinned and couples the shipped runtime to the consumer's NDK version.

### 5.2 A second plugin with its own copy

**Expected outcome, to be measured by T1.9b with the fixture:** AGP fails the app's `merge<Variant>NativeLibs` with "2 files found with path `lib/<abi>/libc++_shared.so`" (`duplicateFailure`). Option 2 has **no library-side resolution**:

- `packaging.jniLibs.pickFirsts` takes effect in the module that packages the APK — the application — not in a library module.
- A plugin cannot set it on the application from its own script: Flutter's app template evaluates `:app` first (`subprojects { project.evaluationDependsOn(":app") }` in the generated root `build.gradle.kts`), so by the time this plugin's script runs, the app's DSL is finalized and its variant callbacks have fired.

So the resolution Option 2 can define is the consumer's: `android { packaging { jniLibs { pickFirsts += "**/libc++_shared.so" } } }` in `android/app/build.gradle.kts` — a manual native edit, which step 1 forbids, in exactly the configuration step 9 is about; and `pickFirst` picks by merge order, not by version, so which NDK's runtime survives is not controllable. The resolution that needs no consumer action is upstream of packaging: **T1.2 links `libTrustWalletCore.so` against `c++_static`**. Upstream's C API is plain C (`TW*`), so no C++ object crosses the library boundary — the condition under which the NDK documents a static runtime as safe — and with no `libc++_shared.so` of ours, the other plugin's copy is the only one (`singleCopy`). That is a T1.2/DECISION-9 build choice, recorded here as evidence; it is not packaging-option-specific and applies to Option 1 equally.

The 16 KB half of step 8 has the same shape: `useLegacyPackaging = false` in this module documents intent, but the APK is packaged under the application's options, where AGP's default for `minSdk >= 23` is already uncompressed, page-aligned native libraries (16 KB-aligned from AGP 8.5.1, per Android's 16 KB page-size guidance; not measured here). `alignment-apk` (`zipalign -c -P 16`) on the consumer's APK is the check.

## 6. The xcframework: assembly, signing, and what it means for the manifest

### 6.1 Assembly (the local dylib set)

For each slice, after both fetch passes: the verified dylib is **moved** into `<slice>/TrustWalletCore.framework/TrustWalletCore`; `lipo -archs` is checked against the manifest `abi` (`arm64`, `arm64_x86_64`); `install_name_tool -id @rpath/TrustWalletCore.framework/TrustWalletCore` (the dylibs are built as `@rpath/libTrustWalletCore.dylib`, which inside a framework would name a file the bundle does not contain); an `Info.plist` (`FMWK`, `CFBundleShortVersionString`/`CFBundleVersion` = the upstream tag because App Store validation wants numbers, `MinimumOSVersion` from the record, and `WCFArtifactSetId`/`WCFUpstreamCommit` for traceability — nothing reads them at run time; the run-time identity is `wcf_build_info()`); `PrivacyInfo.xcprivacy`; then `codesign --force --sign - --timestamp=none` on the bundle. The xcframework's own `Info.plist` (slice table, `XFWK`) is written directly rather than by `xcodebuild -create-xcframework`, so `pod install` does not depend on a working `xcodebuild` and the output is byte-stable for a given manifest. All four plists pass `plutil -lint`; the measured result is ad-hoc signed with the `Info.plist` bound and one sealed resource.

### 6.2 What is and is not verified

The fetch tool verifies the **inputs**. The bytes that ship are not those bytes: the install-name rewrite and the signature change them (+154,376 B on the device slice). The xcframework is a deterministic function of verified inputs, re-checked by the script phase against the digests recorded at assembly — but nothing ties those assembled bytes to anything we published, and no publisher signature can be applied on the consumer's machine without shipping a private key. PRD §12.2 step 10's "sign the xcframework [REC]" is therefore **unreachable** under consumer-side assembly.

### 6.3 Signing

Device and simulator bundles are ad-hoc signed at assembly. When the app is signed, CocoaPods' `[CP] Embed Pods Frameworks` re-signs the embedded framework with the app's identity (`code_sign_if_enabled`); a `--no-codesign` archive leaves the ad-hoc signature. The signed-archive row is step 3's (T1.9b).

### 6.4 Recommendation for T1.2: ship the xcframework zip

The podspec already handles it, and the root manifest already has the row. T1.2's Apple job would run this same assembly in CI (`tool/option2/prepare_xcframework.dart` is reusable as is), sign the xcframework with the project identity once T4.5 provides one, and publish the zip. The manifest row it implies:

## 7. CocoaPods vs Swift Package Manager

This evaluation authors CocoaPods only. Flutter 3.44.1 printed, for this plugin, "The following plugins do not support Swift Package Manager for ios: wallet_core_flutter_native. **This will become an error in a future version of Flutter**" — measured on every `pod install` on 3.44.1, with SwiftPM support disabled in this machine's Flutter config (still `enable-swift-package-manager: false` on 3.47.5). **Flutter 3.47.5 prints it too** (orchestrator-runs, 2026-10-01 and 2026-10-02, recorded verbatim in the `pod-integration` row's `swiftpm_notice` value): "The following plugins do not support Swift Package Manager for ios: - wallet_core_flutter_native This will become an error in a future version of Flutter. Please contact the plugin maintainers to request Swift Package Manager adoption." The warning has not yet become an error across 3.44.1 → 3.47.5. SPM support would add `ios/wallet_core_flutter_native/Package.swift` with a `.binaryTarget(name: "TrustWalletCore", url: <zip URL>, checksum: <sha256>)`: SPM verifies the zip's SHA-256 itself, needs no CocoaPods, and removes that deprecation risk. Its costs are structural: `Package.swift` is sandboxed and cannot run a tool, so there is no equivalent of the podspec's evaluation hook — the xcframework must already exist as a published zip (§6.4), or as a local `path:` binary target present before package resolution; the checksum lives in `Package.swift`, a second copy of the manifest digest that a generator must keep in step; `--vendored`/`--offline` have no native equivalent (SPM resolves from its own URL); and the privacy manifest becomes an SPM resource. SPM is therefore reachable only after T1.2 ships the zip, and is a second iOS integration to maintain beside CocoaPods for as long as Flutter supports both.

## 9. Risks

1. **Flutter's SwiftPM migration.** The warning, measured on 3.44.1 and again on 3.47.5, says a podspec-only plugin will become an error in a future Flutter. Option 2's iOS half has a stated end of life unless §7 is built.
2. **Side effects at podspec evaluation.** Producing files while CocoaPods loads a spec is not a documented CocoaPods extension point; a CocoaPods change to when or how often path podspecs are evaluated breaks it. Mitigated by memoizing per process and by the build-time script phase, which fails a build whose xcframework is missing or stale.
3. **Writes into the pub cache.** For a hosted package the pod directory is the pub-cache copy: shared by every app on the machine, wiped by `dart pub cache repair`, and contended by two concurrent `pod install`s. The prepare step's lock (§1.1) serializes those, so the stamps always describe the set the stamping run verified; the first version had no lock and a private-looking work directory that was shared, and a concurrent `pod install` could make an app link another manifest's set with its own manifest's stamps (review finding 2). Two apps using different `WCF_MANIFEST`s on one machine still overwrite each other's xcframework: the last `pod install` wins, and the other app's next build fails in the script phase (its manifest's digest is not the stamp's) — unless the replacement lands after that build's script phase ran and before it links and embeds the framework, a window the phase cannot see. The lock does not cover that window; a per-app copy of the xcframework would, and Option 2 as built has none.
4. **Consumer-side assembly ships bytes nobody published** (§6.2) and cannot be publisher-signed. Resolved by §6.4.
5. **Android is authored, not run.** The Groovy task class, the Variant API wiring and the error path have never executed (no artifact, no Maven); T1.9b's first build is their first test.
6. **A library module cannot set the application's packaging** (§5.2): `libc++_shared.so` conflicts and 16 KB packaging depend on the app's settings and AGP defaults.
7. **APK bytes differ from the manifest.** AGP strips debug symbols from packaged `.so` files with the app's NDK, so the export check must run on the APK's copy — which `run_eval.sh` does — not be inferred from the artifact's.
8. **User-script sandboxing is off** for this pod's target, a setting Xcode's own defaults move away from.
9. **The pod's deployment target is a toolchain fact, not a library fact.** It is fixed at 15.0 because of Xcode 27 and Flutter 3.47; a future Xcode that raises its floor again breaks every app on an older Flutter template first (as 3.44.1 broke on Xcode 27.0), and the pod's value must follow. The library's own minimum (13.0 device, 14.0 / 13.0 simulator arm64 / x86_64) no longer constrains anything.
10. *(Resolved.)* The 3.44.1 consumer's `project.pbxproj` carried the local keychain's `DEVELOPMENT_TEAM`; the 3.47.5 regeneration ran `flutter create` with an empty `HOME`, and the committed file has none.

## 11. What the harness could not do

- **No pod-integration check.** The catalogue has no row for what `pod install` integrated; the evaluation writes `pod-integration` / `ios/pod`, which renders under "Results with no catalogue row".
- **`report.dart` argument parsing.** Every argument not starting with `-` is taken as a results path, including the value of a space-separated `--out FILE` or `--title TEXT`; `run_eval.sh` uses the `--name=value` forms.
- **`consumer_gen` cannot keep its loopback repository alive for a build**, so the built consumer resolves the packages by path from staged copies, and hosted consumption (step 11) is measured on a separate, unbuilt app.
- **No command for evaluation-owned rows** (a build, an on-target run, the wrong-digest fixture); `eval/option2/tool/eval.dart row` writes them in the harness schema.

None of these needed a harness change; each is reported here rather than worked around inside `tools/`.
