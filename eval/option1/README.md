# DECISION-2 Option 1 — build hooks: evaluation

Unofficial Dart/Flutter SDK for the open-source Trust Wallet Core library. Not affiliated with or endorsed by Trust Wallet.

**Evaluation branch only (`eval/option1`).** Nothing here merges unless Option 1 wins DECISION-2 at D1a. The findings are in [`docs/decisions/DECISION-2-option1.md`](../../docs/decisions/DECISION-2-option1.md); this file says what is here and how to run it.

## What is here

| Path | What |
|---|---|
| `run_eval.sh` | PRD §12.2 steps 1–11, in order, through `tools/packaging_eval`. Writes `results/results.jsonl`, renders `results/table.md`, and re-embeds that table and the row counts into `docs/decisions/DECISION-2-option1.md` §2.1. |
| `eval_manifest.json` | **Evaluation-only** manifest: the root `compat_manifest.json` with the Apple rows and identity of the locally built set `as_4.8.0_000` (never published). Generated by `tool/make_eval_manifest.dart`; `run_eval.sh` checks it is current. |
| `consumer/` | The consumer app: `flutter create`, then the edits listed below — no Podfile, Gradle or Xcode project edit. |
| `tool/create_consumer.sh` | How `consumer/` was generated. |
| `tool/make_eval_manifest.dart` | Writes (or `--check`s) `eval_manifest.json` from `third_party/wcf-native-all/records/`. |
| `tool/eval_tool.dart` | The rows the harness leaves to an evaluation (a build, a run, the offline and wrong-digest checks), in the harness's schema; the two verdicts that read the hook's own output (`classify-negative`, `offline-evidence`); the list of embedded frameworks to scan for duplicates; the path rewrite of committed rows; the table embed; manifest reads; staged copies. Measures nothing. |
| `tool/verdicts.sh` | Sourced by `run_eval.sh`: when a packaged-binary row may be measured, when an offline row may say `pass`, and the guard that `consumer/` is still as `flutter create` wrote it. |
| `results/` | The last run's rows and table. Written only by `run_eval.sh`; never edited by hand. |

The verdict logic of `tool/eval_tool.dart` and `tool/verdicts.sh` is tested by `packages/wallet_core_flutter_native/test/eval_option1/`, so `melos run test` covers it.

## Running it

```sh
eval/option1/run_eval.sh
```

Needs: macOS with Xcode and Flutter; the git-ignored local artifact set `third_party/wcf-native-all/` (built by `tools/native_build/`); for the simulator rows, an iOS simulator **already booted** (the script never boots, erases or configures one). Every app is built in a fresh copy of `consumer/` staged at `$TMPDIR/o1/app` (`eval_tool.dart stage`: no `build/`, `.dart_tool/` or CocoaPods/SwiftPM state), so no build reuses an earlier run's outputs or hook cache, and every packaged binary measured is this run's. **Nothing runs inside `consumer/`**: any `flutter` command there — even `flutter test`, through its `flutter pub get` — copies Flutter's Podfile template into `ios/` and adds `#include? "Pods/…"` to the xcconfigs, because the app has an iOS plugin and Swift Package Manager is off (T1.8a delta 5). The script refuses to start, and exits 1 at the end, if `consumer/` has a Podfile, a `Pods` reference, SwiftPM state or a pub-generated macOS plugin registrant (`pristine_check` in `tool/verdicts.sh`). Scratch copies, logs and generated apps go under `$TMPDIR/o1` (deleted at the start of each run). Flutter, Xcode and pub write their usual caches.

Every row it cannot measure is `unmeasured` with the exact command — including a measurement of an app whose build did not succeed in the same run (`not built in this run`). Android rows wait for the first Android artifact (no `.so` exists, T1.2); physical-device rows are T1.8b's.

**Toolchain.** The evaluation runs on Flutter 3.47.5 / Dart 3.13.4 with Xcode 27.0, and `consumer/` was generated by that Flutter (iOS 15.0 / macOS 12.0 deployment targets). Flutter 3.44.1 could not build any iOS app on Xcode 27.0 — its template writes iOS 13.0 / macOS 10.15, below Xcode 27.0's minimums of 15.0 / 12.0, so even an empty `flutter create` app failed; that is why the first orchestrator runs stopped at the first Xcode build, and why 3.44.1 says nothing about either packaging option. The script reads the Flutter, Dart and Xcode versions and the generated deployment targets at run time; no version is written into it.

The macOS desktop app is not a required target. Where a host's Xcode rejects the template's `MACOSX_DEPLOYMENT_TARGET` (as with 3.44.1 above), that is independent of either packaging option, fixing it would be a native edit, and macOS desktop is outside PRD §12.2 — so the script records it as `skip`, with the template value and the Xcode range taken from the build log (any other macOS-app failure as `fail`), and continues. On 3.47.5 the macOS build stops instead at Flutter's `Podfile missing`: the consumer's only native plugin, the `integration_test` dev dependency, supports Android and iOS only. Flutter therefore runs CocoaPods for macOS but never writes `macos/Podfile`, because Swift Package Manager is off for macOS on that host. This is a Flutter tooling gap, also recorded as `skip` with its cause.

Failures of the required targets (iOS simulator debug, the iOS device release archive) still stop the run. The host `flutter test` rows never do: the script runs the host test from two staged copies, under `$TMPDIR` and under `/tmp/wcf-o1-<pid>`, a short directory it creates and removes (the one place it writes outside `eval/option1/results/`, `docs/decisions/DECISION-2-option1.md` and `$TMPDIR`). The bundled dylib's install name must fit in 87 characters, and the default macOS `$TMPDIR` is already too deep for that. (Until delta 5 a third host test ran in the checkout itself; it was dropped, see `DECISION-2-option1.md` §12.) The simulator app is measured from a copy taken right after its build, against a baseline app with the same plugin set.

Two verdicts read the hook's own output. **Offline:** each target's offline row is its first build in a fresh staged copy, and passes only if the hook's log (`.dart_tool/hooks_runner/wallet_core_flutter_native/<config>/stdout.txt`) showed nothing for the artifact before the build and a copy from `vendored_dir` with `offline` set after it; a warm cache is `unmeasured`. **Wrong digest:** the build passes only if it fails *and* its output carries the hook's one-line `<artifact>: sha256 mismatch: expected <the flipped digest> …` verdict; the generic "could not be verified" headline, which every fetch failure prints, does not count. Every row — the harness's included — names paths repo-relative, `$TMPDIR`-relative or `~`-relative (`eval_tool.dart relativize`, run before rendering), so committed results name no home directory.

## The evaluation manifest

Three values differ from the local set's own records, each forced by a validator and none of them a digest:

- `build_workflow` (identity and per artifact): the records say `local`; `tools/manifest` requires an `https://` URL, so it reads `https://wcf-eval-only.invalid/local-build/as_4.8.0_000`. `.invalid` is reserved (RFC 2606, RFC 6761) and can never resolve. The runtime identity check does not compare `build_workflow`.
- `retention.primary`: the root's `TBD-T0.11` is refused by the fetch tool's manifest gate even for a vendored, offline fetch, so it reads `https://wcf-eval-only.invalid/never-published/as_4.8.0_000`. A download attempt against it fails closed at DNS; the consumer builds with `offline: true`, so none is made.
- `ios/TrustWalletCore.xcframework.zip` is replaced by the three per-slice dylibs, because a build hook bundles one library per SDK and architecture.

The digests and sizes are the records', and `make_eval_manifest.dart` writes one only after hashing the file it describes. `third_party/` is untrusted input: `run_eval.sh` re-verifies every pinned file against this manifest before measuring anything, and the hook verifies again before bundling.

## Files changed after `flutter create`

`tool/create_consumer.sh` generated `consumer/` with Flutter 3.47.5 (with an empty `HOME`, so no signing team was written into the Xcode projects, and without the IDE files); it was regenerated from scratch when the host moved from 3.44.1, and the files below re-applied. After it:

| File | Change |
|---|---|
| `consumer/pubspec.yaml` | added `ffi`, path dependencies on `wallet_core_flutter_bindings` and `wallet_core_flutter_native`, a `dependency_overrides` entry for `wallet_core_flutter_native` (the bindings pin it as a hosted `0.0.1`), `integration_test`, and the `hooks.user_defines.wallet_core_flutter_native` block |
| `consumer/pubspec.lock` | regenerated by `flutter pub get` |
| `consumer/lib/wallet_core_probe.dart` | **new** — load, identity, symbol resolution, one real call |
| `consumer/lib/probe_main.dart` | **new** — entry point for a release run on a device |
| `consumer/integration_test/wallet_core_test.dart` | **new** — the in-app check |
| `consumer/test/bundled_library_test.dart` | **new** — the host-side check under `flutter test` |

`lib/main.dart`, `test/widget_test.dart`, and everything under `ios/`, `macos/` and `android/` are as `flutter create` wrote them. (T1.8a-d4 re-checked this against a fresh `flutter create` of Flutter 3.47.5 with the flags of `tool/create_consumer.sh`, after removing what the earlier in-place Xcode builds had added — `ios/Podfile`, `Podfile.lock`, the `Pods` references in `Runner.xcodeproj`, `Runner.xcworkspace` and the two xcconfigs, and SwiftPM state; the three folders are now byte-identical to that output. Delta 5 removed the Podfile and xcconfig includes the in-place host test had written, and re-checked the same way.)

Path dependencies, not hosted ones, because this app is built from a checkout (staged copies make them absolute). Hosted consumption (PRD §12.2 step 11) is measured by `tools/packaging_eval/bin/consumer_gen.dart`, which `run_eval.sh` runs.
